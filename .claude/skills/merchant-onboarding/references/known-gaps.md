# Known gaps (verified against code and docs, 2026-11; the unpaid-shipment and expired-invitation gaps were closed by change `order-and-invitation-polish`)

Re-verify before relying on one: platform behaviour changes with each openspec change. "Evidence" says where it was checked. Do not work around a gap by editing platform code during onboarding; tell the operator.

## Platform limitations

1. **No email delivery for admin account links.** Password setup, password reset and staff invitation links are returned in the API response with `delivery:"manual"` (`setup_url` / `reset_url` / `invite_url`), shown once, never retrievable again. The operator must pass them to the person securely, and consumers must branch on `delivery`, not on whether the URL field exists. Evidence: `.env.example` ("Until the VPS move there is no outbound mail for admin accounts"), `docs/admin-frontend-integration.md`. Customer order emails (order placed, payment succeeded) do exist via SMTP, from one platform-wide sender; Gmail limits apply (about 100 mails/day free, a few dozen paid orders a day for the whole platform), see `.env.example`.
2. **ECPay stage vs production is platform-wide.** `ECPAY_CHECKOUT_URL` points the whole deployment at one ECPay environment; per-shop credentials (MerchantID/HashKey/HashIV) are stored per shop but cannot select the environment. One deployment cannot run one shop on stage and another in production. Evidence: `.env.example` ("THE ONLY DIFFERENCE BETWEEN SIMULATED AND LIVE OPERATION ... platform-wide").
3. **Only `merchant_owner` can set payment credentials** (`payment_credential.manage`); `editor` and `staff` cannot, and credentials are write-only (never readable, only a configured flag). The platform operator therefore cannot enter them on the owner's behalf without the owner's login. Evidence: openapi `putECPayCredentials`.
4. **Provisioning does not create the publishable key, shipping methods, categories, tiers, products or payment credentials.** `setup-status` reports exactly these as unfinished. Evidence: `api/internal/provision/service.go` (shop, owner, origins;).
5. **No generic catalogue importer in the platform.** The only platform seeder is `make seed-demo` (demo shop); the merchant template ships `scripts/import-catalog.mjs` (JSON input, idempotent, never deletes). `api/cmd` has `ecpay-sim`, `migrate`, `migrategen`, `sanitize-content`, `seed`, `server`.
6. **Allowed origins are platform-managed, global and exact.** No wildcards, one purpose per origin, unique across all shops, only `shop.manage_client_origins` can register them. Random-hash preview domains (e.g. Pages previews) cannot be covered; register fixed preview domains. Evidence: `docs/storefront-integration.md` section 1, openapi `createAllowedOrigin`.
7. **Platform-level admin API is not reachable by an agent in production.** It answers only on `PLATFORM_ADMIN_HOSTS` behind a Cloudflare Access policy for the platform owner; the merchant admin hosts are bound to their own shop and get 403 on platform paths. Evidence: runbook sections 3b, 5, 6.
8. **Everything in Cloudflare (R2, Tunnel, Access, DNS) is manual.** Nothing in the repos applies it; the example tunnel config is merged by hand. Every new merchant admin hostname must be added to the merchant Access application, the tunnel ingress, DNS and the R2 CORS list.
9. **Image orphan cleanup is not built.** Failed object deletes leave orphan files in the bucket (WARN log with shop id and key); cleanup command is listed as future work. Evidence: `docs/media-r2-setup.md`. Uploads accept JPEG/PNG/WebP only; HEIC must be converted by each admin front end.
10. **Merchant admin Access policy is "everyone with a one-time PIN".** Authorization is entirely application RBAC plus host binding; `CF_ACCESS_BIND_EMAIL` is off by default. Evidence: runbook 3a/5.
11. **Account lockout can be used against a victim**: 10 wrong passwords for an email lock it for 15 minutes from all IPs (429 even with the right password). Evidence: openapi `adminLogin`.

12. **No automated intake yet.** New merchants enter this playbook by operator decision. The platform website with a public application form, email verification, admin review and approval-triggered provisioning is planned (OpenSpec change `platform-website`, a proposal with open questions); nothing of it exists. Until then step 0 is manual, and the owner's setup link is handed over by the operator.
13. **The hosted-storefront features are gone (removed 2026-11-25, change `retire-hosted-storefront-and-themes`, ADR 0002).** No themes, no sites/Host resolution, no `web/` storefront; `setup-status` has no `theme_applied`/`domain_bound`; the provisioning request has no `theme_id`/`domain`/`path_prefix`. Consequence to know about: a newly provisioned shop has **no content schema** until a human registers one (`PUT .../content/schema`, built 2026-11-25, gap 15), and creating CMS pages on it returns 422 with a message naming that call; every new shop still gets an empty CMS home page row. Evidence: `api/internal/provision/status.go`, `api/internal/contentschema/`.
14. **SMTP exists but only for order emails, and is usually unconfigured.** `notify.Sender` / `SMTPSender` serve the two customer order emails when `SMTP_USERNAME`/`SMTP_PASSWORD` are set; admin account links and the planned application emails have no delivery path yet (manual hand-over). Evidence: `api/internal/app/wire.go`, `api/internal/account/delivery.go`.

## Doc and template inaccuracies noticed (report, do not edit during onboarding)

- `.env.example` does not list `CORS_ALLOWED_ORIGINS`, `PLATFORM_ADMIN_HOSTS`, `CF_ACCESS_TEAM_DOMAIN`, `CF_ACCESS_AUD`, `CF_ACCESS_BIND_EMAIL`; they are only in the runbook and `api/internal/config/config.go`.
- The OpenAPI file is `api/openapi/openapi.yaml` (several docs and requests say `openapi/openapi.yaml`).
- (Resolved in the template) The earlier site docs said the platform's checkout idempotency was not yet enforced; the platform repo records `checkout-idempotency` as archived (implemented) and `docs/storefront-integration.md` section 5.5 documents it. Confirm what is deployed.
- (Resolved in the template) `config.js` placeholders versus the guard: `template.json` `isTemplate` now decides. Placeholders are enforced in the template only; a merchant repo's real `apiBase` / `publishableKey` are written by `scripts/new-merchant.mjs` or a human, protected by the manifest hash, and never overwritten by `sync-core.mjs`.
- The example tunnel config points every admin hostname at the same static port (`127.0.0.1:3001`); with more than one merchant admin build each needs its own port or directory.
15. **The content store is partly built.** Built (first slice of OpenSpec change `headless-content-store`, 2026-11-25): per-shop content schema registration (`PUT/GET /api/v1/admin/shops/{id}/content/schema`, versions, dry run, removal confirmation, `needs_attention`, human-only `content.manage`) and the `content.*` permission nodes with `page.*` as aliases; a shop with a registered schema can create and publish pages. **Not built**: content documents addressed by key, revisions/restore, the public `GET /shop/content*` endpoints and preview token, the publish hook, a `content_schema_registered` setup-status flag, and everything in the merchant template (no `content.schema.json` in `designPaths`, no `ShopCommerce.content`, no admin content screens, no schema sync action). So the merchant's copy still lives in the design layer (`public/content.js`) and the storefront does not read the content store; the slug-keyed `/pages` and `/render/page` endpoints work but are not what the template consumes. Steps: `SKILL.md` 11a and `references/checklist.md`. Evidence: `docs/content-schema.md`, `api/internal/content/`, `openspec/changes/headless-content-store/tasks.md`.
