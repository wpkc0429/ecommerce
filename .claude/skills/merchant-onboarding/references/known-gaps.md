# Known gaps (verified against code and docs, 2026-11)

Re-verify before relying on one: platform behaviour changes with each openspec change. "Evidence" says where it was checked. Do not work around a gap by editing platform code during onboarding; tell the operator.

## Platform limitations

1. **No email delivery for admin account links.** Password setup, password reset and staff invitation links are returned in the API response with `delivery:"manual"` (`setup_url` / `reset_url` / `invite_url`), shown once, never retrievable again. The operator must pass them to the person securely, and consumers must branch on `delivery`, not on whether the URL field exists. Evidence: `.env.example` ("Until the VPS move there is no outbound mail for admin accounts"), `docs/admin-frontend-integration.md`. Customer order emails (order placed, payment succeeded) do exist via SMTP, from one platform-wide sender; Gmail limits apply (about 100 mails/day free, a few dozen paid orders a day for the whole platform), see `.env.example`.
2. **Invitation list hides expired invitations.** `GET /api/v1/admin/shops/{id}/invitations` lists only pending, unexpired, unrevoked ones; an expired invitation cannot be seen or revoked, and re-inviting the same email replaces the old one. Evidence: `listShopInvitations` description in `api/openapi/openapi.yaml`.
3. **Shipments can be created for unpaid orders at the API level.** `createShipment` only answers 409 for a cancelled order, nothing left to ship, or an order already marked returned; there is no payment-status precondition (`api/internal/shipping/service.go` `CreateShipment`). The bouquet admin blocks it in the UI (`shipBlocker` returns `unpaid`), which is an experience layer, not authorization. A different admin front end could ship unpaid orders. Evidence: openapi `createShipment`, service code.
4. **ECPay stage vs production is platform-wide.** `ECPAY_CHECKOUT_URL` points the whole deployment at one ECPay environment; per-shop credentials (MerchantID/HashKey/HashIV) are stored per shop but cannot select the environment. One deployment cannot run one shop on stage and another in production. Evidence: `.env.example` ("THE ONLY DIFFERENCE BETWEEN SIMULATED AND LIVE OPERATION ... platform-wide").
5. **Only `merchant_owner` can set payment credentials** (`payment_credential.manage`); `editor` and `staff` cannot, and credentials are write-only (never readable, only a configured flag). The platform operator therefore cannot enter them on the owner's behalf without the owner's login. Evidence: openapi `putECPayCredentials`.
6. **Provisioning does not create the publishable key, shipping methods, categories, tiers, products or payment credentials.** `setup-status` reports exactly these as unfinished. Evidence: `api/internal/provision/service.go` (shop, theme, domain, owner, origins only).
7. **No generic catalogue importer in the platform.** The only seeders are `make seed-demo` (demo shop) and the bouquet template's `scripts/seed-test-shop.mjs` (test data, to be forked and edited). `api/cmd` has `ecpay-sim`, `migrate`, `migrategen`, `sanitize-content`, `seed`, `server`.
8. **Allowed origins are platform-managed, global and exact.** No wildcards, one purpose per origin, unique across all shops, only `shop.manage_client_origins` can register them. Random-hash preview domains (e.g. Pages previews) cannot be covered; register fixed preview domains. Evidence: `docs/storefront-integration.md` section 1, openapi `createAllowedOrigin`.
9. **Platform-level admin API is not reachable by an agent in production.** It answers only on `PLATFORM_ADMIN_HOSTS` behind a Cloudflare Access policy for the platform owner; the merchant admin hosts are bound to their own shop and get 403 on platform paths. Evidence: runbook sections 3b, 5, 6.
10. **Everything in Cloudflare (R2, Tunnel, Access, DNS) is manual.** Nothing in the repos applies it; the example tunnel config is merged by hand. Every new merchant admin hostname must be added to the merchant Access application, the tunnel ingress, DNS and the R2 CORS list.
11. **Image orphan cleanup is not built.** Failed object deletes leave orphan files in the bucket (WARN log with shop id and key); cleanup command is listed as future work. Evidence: `docs/media-r2-setup.md`. Uploads accept JPEG/PNG/WebP only; HEIC must be converted by each admin front end.
12. **Merchant admin Access policy is "everyone with a one-time PIN".** Authorization is entirely application RBAC plus host binding; `CF_ACCESS_BIND_EMAIL` is off by default. Evidence: runbook 3a/5.
13. **Account lockout can be used against a victim**: 10 wrong passwords for an email lock it for 15 minutes from all IPs (429 even with the right password). Evidence: openapi `adminLogin`.

## Doc and template inaccuracies noticed (report, do not edit during onboarding)

- `.env.example` does not list `CORS_ALLOWED_ORIGINS`, `PLATFORM_ADMIN_HOSTS`, `CF_ACCESS_TEAM_DOMAIN`, `CF_ACCESS_AUD`, `CF_ACCESS_BIND_EMAIL`; they are only in the runbook and `api/internal/config/config.go`.
- The OpenAPI file is `api/openapi/openapi.yaml` (several docs and requests say `openapi/openapi.yaml`).
- Bouquet `README.md` and `CLAUDE.md` still say the platform's checkout idempotency is "not yet enforced / not yet live", while the platform repo records `checkout-idempotency` as archived (implemented) and `docs/storefront-integration.md` section 5.5 documents it. Confirm what is deployed.
- Bouquet `README.md` says to replace the `public/config.js` placeholders before deploying, but `scripts/check-layers.mjs` fails if they are replaced (and if the file hash changes). The template needs a defined way to supply the merchant's `apiBase` and `publishableKey`.
- The example tunnel config points every admin hostname at the same static port (`127.0.0.1:3001`); with more than one merchant admin build each needs its own port or directory.
