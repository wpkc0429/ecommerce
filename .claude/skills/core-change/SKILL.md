# Core change (human-reviewed, platform admin)

**An AI design session never performs a core change and never runs `check-design.mjs --update`, `gen-public-api.mjs` or `sync-design.mjs`.** If you are in a design session and the request needs anything below, write the proposal and stop. Only a human maintainer, in a FULL checkout of `ecommerce` on a branch (e.g. `core/admin-<topic>`), does "Doing it". Commands run from `admin/` unless stated.

## What counts as a core change

Any change to a file under `admin/` other than `design/`, `docs/`, `e2e/` (the hash manifest is deny-by-default: even a new file, `README.md` or `CLAUDE.md` is locked). In particular: a new or changed `ctx` name (`ctx.data|actions|logic|enums|ui|format|auth`), a new irreversible action and its warning, a new copy key, a changed permission/validation/state rule, `styles.css`, `nginx.conf`/CSP, `Dockerfile`, the guards in `scripts/`, `lib/meta/*.js` (routes, nav, fixed warnings), `design-defaults/`. Files only in `design/` are NOT a core change.

## Proposing (what an AI session or developer hands over)

State: what the request needs; why the design layer cannot do it; the locked files involved; the smallest design (new `ctx` name and signature, permission node via `need` / `needAny` / `needPlatform`, state rule, validation, error cases, copy keys with default wording, whether it is irreversible); the effect on the current `design/` (will it need an action or a `sync-design`?). Do not edit anything.

## Doing it

### Files that must change together

| Change | Files |
| --- | --- |
| New `ctx` function / action | implementation in `core/groups/<group>.js` (permission check first via `core/guard.js`; every API call through `lib/api.js`; errors as `ActionError` from `core/errors.js`); `lib/public-api.json` regenerated by `node scripts/gen-public-api.mjs` (review the diff: it IS the contract change); `docs/DESIGN-LAYER.md` section 4; a default view in `design-defaults/views\|parts/` if a screen uses it; guard fixtures `scripts/__fixtures__/cases.mjs` / `scripts/test-guard.mjs` only when a scan rule is involved; e2e coverage in `../e2e/` |
| New copy key | `design-defaults/copy/<file>.js` (aggregated by `design-defaults/copy.js`), then `design/copy.js` through sync (below) |
| New route | `lib/meta/<group>.js` (`routes` and `nav`; `ROUTE_IDS` derives from it), a default view in `design-defaults/views/<kebab-id>.js`, `design/routes.js` via sync |
| New IRREVERSIBLE action | the action asks through `confirmDialog({ ..., warning })` (see `core/groups/*.js` for the pattern); add `<id>: "fixed warning"` to `warned` in `lib/meta/<group>.js` (the single source: `WARNED_CONFIRM_IDS` and `core/warnings.js` derive from it); copy keys `confirm.<id>.title`, `.text` (lead-in, may be empty), `.yes` (and `.no` if used) in `design-defaults/copy/`, never `.warning` or `.message`; list the id in `docs/DESIGN-LAYER.md` section 2; e2e clicks it with `armConfirm(page)` |
| CSP | `nginx.conf` (and `CSP` in `scripts/serve.mjs`, which must match), `deployChecks` in `scripts/check-design.mjs` and its tests, `README.md` |
| Any locked file | the hash manifest (below) |

### Sync the defaults into the design layer (HUMAN ONLY)

`node scripts/sync-design.mjs` regenerates `design-defaults/routes.js` and `design/routes.js`, rewrites `design/copy.js` from `design-defaults/copy.js`, and REPLACES `design/views` and `design/parts` with the defaults. **It overwrites every design customisation.** Run it only when `design/` has nothing to keep, or after saving the diff of `design/` and re-applying it. For a small change, the alternative is to edit the same lines by hand in `design/` and `design-defaults/` so both agree.

### Re-locking the manifest (HUMAN ONLY)

First run the guard WITHOUT `--update` and read what it reports: every `manifest/changed` line must be a file you meant to change, and every other step must already be green.

```bash
node scripts/check-design.mjs                 # lists manifest/changed lines
# only then, as the maintainer (never to "make the guard pass" without reading it):
node scripts/check-design.mjs --update        # rewrites scripts/core.manifest.json
git diff --stat scripts/core.manifest.json    # review: only the intended files' hashes moved
```

### Tests (all must pass)

```bash
node scripts/check-design.mjs
node scripts/test-guard.mjs
node scripts/check-layers.mjs
```

When behaviour or screens changed, also run the browser e2e on a THROWAWAY stack (root `CLAUDE.md`: `ecommerce_e2e` database, second API on :8180 with `REDIS_DB=1`; never the main database, tunnel or Cloudflare; never `docker compose down -v`): `cd ../e2e && node happy-path.mjs`, and for visual changes `node parity.mjs capture <dir>` then `compare`. Update the counts in the root `CLAUDE.md` if they change.

### Record it

Update `admin/docs/DESIGN-LAYER.md` (and the root `CLAUDE.md` block "admin 的鎖定核心與設計層" if the contract changed). Commit logically, with the regenerated `public-api.json` and the manifest in the same commit as the files they describe. Core paths need a human reviewer; `design/**` branches may be merged after operator approval.

## Never

- Run `--update` to silence a guard you have not read; widen the unlocked prefixes in `check-design.mjs` to unlock something; edit `design/` inside a core change to hide a failure.
- Let an AI session, CI, a hook or the AI edit service run any of this.
- Weaken a confirmation warning, the CSP or a guard "temporarily".
