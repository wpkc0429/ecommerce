## Requirements
### Requirement: ECPay AIO provider implements the payment provider abstraction

系統 MUST 提供一個名為 `ecpay` 的 `Provider` 實作，涵蓋綠界全方位金流（AIO）的**真實線路形狀**：`AioCheckOut V5` 的欄位集、`CheckMacValue` 檢查碼、以及付款結果通知（`ReturnURL`）的解析與回應約定。它 MUST 註冊進既有的 provider registry，並且 MUST NOT 需要修改 `payment.Service.HandleWebhook` 的控制流程——**每商家憑證解析**（change ecpay-per-shop-credentials）例外於這條保證的是路由本身，而不是控制流程：`ecpay` 的憑證是逐商家解析的，webhook 驗簽在資訊上必須先知道要用哪個商家的密鑰，因此 `ecpay` 的 webhook 額外使用一個帶 shop id 的路由形狀（見 spec `payment-integration`）；`HandleWebhook` 內部由 `(provider, provider_reference)` 定位付款記錄、CAS 推進狀態的邏輯逐字不變。發起付款時 MUST 送出綠界要求的全部必填欄位，且 `PaymentType` MUST 固定為 `aio`、`EncryptType` MUST 固定為 `1`（SHA256）。

#### Scenario: 發起付款產生完整的綠界欄位集
- **WHEN** 對一張 TWD 訂單以 `ecpay` provider 發起付款
- **THEN** 回傳的表單欄位集包含 `MerchantID`、`MerchantTradeNo`、`MerchantTradeDate`、`PaymentType`、`TotalAmount`、`TradeDesc`、`ItemName`、`ReturnURL`、`ChoosePayment`、`EncryptType`、`CheckMacValue`，且 `PaymentType` 為 `aio`、`EncryptType` 為 `1`

#### Scenario: 表單送出方式是 POST
- **WHEN** 對一張訂單以 `ecpay` provider 發起付款
- **THEN** 回傳的導向資訊宣告方法為 `POST`、目標為設定的收銀台網址

### Requirement: CheckMacValue is computed by ECPay's published algorithm

`CheckMacValue` MUST 依綠界公開文件的演算法計算：①除 `CheckMacValue` 外所有參數依參數名 **大小寫不敏感** A→Z 排序後以 `&` 串接；②前綴 `HashKey=<key>&`、後綴 `&HashIV=<iv>`；③整串以「.NET 相容」的 URL encode 編碼（空白編為 `+`；`-` `_` `.` `!` `*` `(` `)` MUST 還原為原字元；`~` MUST 維持編碼為 `%7e`）；④全部轉小寫；⑤SHA256；⑥轉大寫十六進位。

實作 MUST 通過綠界官方文件公布的範例向量。

#### Scenario: 官方範例向量
- **WHEN** 以 HashKey `pwFHCqoQZGmho4w6`、HashIV `EkRm7iFT261dpevs` 對官方範例參數集（含中文 `TradeDesc=促銷方案`、含空白的 `ItemName=Apple iphone 15`、含 `:` 與 `/` 的 `ReturnURL`）計算檢查碼
- **THEN** 結果為 `6C51C9E6888DE861FD62FB1DD17029FC742634498FD813DC43D4243B5685B840`

#### Scenario: 排序不區分大小寫
- **WHEN** 參數集中同時含有首字母大寫與小寫的參數名
- **THEN** 排序依大小寫不敏感的字典序，而非 ASCII 序

#### Scenario: 波浪號維持編碼
- **WHEN** 任一參數值含有 `~`
- **THEN** 編碼結果中該字元為 `%7e`，而非原字元

### Requirement: MerchantTradeNo is generated by the platform within ECPay's limits

`MerchantTradeNo` MUST 由本系統產生，MUST 只含英數字，長度 MUST NOT 超過 20 個字元，且 MUST 對每一次付款嘗試都不同（即使是同一張訂單的重試）。產生結果 MUST 被原樣存入 `payments.provider_reference`，作為 webhook 的冪等查找鍵。

若產生的識別碼會超過 20 字元，系統 MUST 回報錯誤，MUST NOT 送出一個綠界必然拒絕的請求。

#### Scenario: 識別碼符合綠界的字元與長度限制
- **WHEN** 為任一訂單產生 `MerchantTradeNo`
- **THEN** 結果只含英數字且長度不超過 20

#### Scenario: 同一訂單的兩次付款嘗試取得不同識別碼
- **WHEN** 對同一張訂單先後發起兩次付款
- **THEN** 兩次的 `MerchantTradeNo` 不同，且對應兩筆獨立的付款紀錄

#### Scenario: 識別碼會超長時明確失敗
- **WHEN** 訂單 id 大到讓產生的識別碼超過 20 字元
- **THEN** 發起付款回報錯誤，不建立付款紀錄

### Requirement: ECPay provider rejects currencies other than TWD

綠界只受理新台幣，且 `TotalAmount` 是整數新台幣元——與本系統「金額為最小貨幣單位整數」的約定在 TWD 下**恰好相等，無任何換算**。此等式只在 TWD 下成立，因此 provider 在發起付款時 MUST 拒絕 `currency` 不是 `TWD` 的訂單，MUST NOT 把其他幣別的金額原樣送出。

送出的 `TotalAmount` MUST 逐位元組等於該筆付款紀錄的 `amount`，MUST NOT 有任何乘除。

#### Scenario: 非 TWD 訂單被拒
- **WHEN** 對一張 `currency` 為 `USD` 的訂單以 `ecpay` provider 發起付款
- **THEN** 回報錯誤，不建立付款紀錄，也不產生任何綠界欄位

#### Scenario: 金額原樣送出
- **WHEN** 對一張 `total_amount` 為 3400、幣別 TWD 的訂單發起付款
- **THEN** 表單欄位 `TotalAmount` 為 `3400`

### Requirement: Payment result notification is verified and acknowledged in ECPay's own protocol

付款結果通知 MUST 以 `application/x-www-form-urlencoded` 的**原始位元組**解析，簽章 MUST 在解析出的全部欄位（`CheckMacValue` 本身除外）上重算比對；比對不符 MUST 視為驗證失敗，MUST NOT 更新任何付款或訂單資料。

通知中未被本系統認識的欄位 MUST 仍然參與檢查碼計算，MUST NOT 被丟棄。

驗證通過後，系統 MUST 以**純文字 `1|OK`** 回應綠界；MUST NOT 回應 JSON 錯誤信封。認不出該筆交易時同樣 MUST 回 `1|OK`（重送不會使它變得認得）。只有在本系統自身處理失敗時，MUST 回應非 `1|OK` 的內容，讓綠界重送。

#### Scenario: 簽章正確的成功通知回 1|OK
- **WHEN** 綠界對一筆待付款的付款紀錄送出 `RtnCode=1`、檢查碼正確的通知
- **THEN** 回應主體恰為 `1|OK`、內容型別為純文字，該付款紀錄轉為成功，訂單 `payment_status` 變為 `1`

#### Scenario: 檢查碼錯誤的通知被拒
- **WHEN** 送出一個 `CheckMacValue` 與內容不符的通知
- **THEN** 付款紀錄與訂單狀態皆不變，回應不是 `1|OK`

#### Scenario: 未知欄位參與檢查碼計算
- **WHEN** 通知中含有本系統未定義的額外欄位，且檢查碼是把該欄位一併計入後算出的
- **THEN** 驗證通過

#### Scenario: 認不出的交易仍回 1|OK
- **WHEN** 送出一個檢查碼正確、但 `MerchantTradeNo` 不對應任何付款紀錄的通知
- **THEN** 回應主體恰為 `1|OK`，不更新任何資料

### Requirement: RtnCode 1 alone does not mean the money arrived

綠界的「模擬付款」功能會送出 `RtnCode=1` 但 `SimulatePaid=1` 的通知，而綠界**不會撥款**；`RtnCode=10300066`（交易付款結果待確認中）同樣既非成功也非失敗。系統 MUST NOT 僅依 `RtnCode=1` 判定付款成功。

上述兩種通知 MUST 被視為**非終局**：MUST NOT 把付款紀錄轉為成功或失敗、MUST NOT 推進訂單付款狀態、MUST NOT 核發點數，且 MUST NOT 讓該筆付款紀錄離開待付款狀態——否則稍後真正的成功通知將無法推進訂單。系統 MUST 仍以 `1|OK` 回應。

#### Scenario: 模擬付款不會讓訂單變成已付款
- **WHEN** 收到 `RtnCode=1` 且 `SimulatePaid=1`、檢查碼正確的通知
- **THEN** 回 `1|OK`，付款紀錄仍為待付款，訂單 `payment_status` 仍為 `0`，未核發任何點數

#### Scenario: 非終局通知之後的真實成功通知仍然有效
- **WHEN** 同一筆付款先收到 `SimulatePaid=1` 的通知，之後收到 `RtnCode=1`、`SimulatePaid=0` 的通知
- **THEN** 第二通使付款紀錄轉為成功、訂單 `payment_status` 變為 `1`

#### Scenario: 待確認狀態不被當成失敗
- **WHEN** 收到 `RtnCode=10300066`、檢查碼正確的通知
- **THEN** 付款紀錄仍為待付款，訂單 `payment_status` 仍為 `0`

#### Scenario: 真正的失敗碼使付款紀錄失敗
- **WHEN** 收到 `RtnCode` 為某個失敗碼（例如 `10100252` 額度不足）、檢查碼正確的通知
- **THEN** 付款紀錄轉為失敗，訂單 `payment_status` 維持 `0`，會員可再次發起付款

### Requirement: Notified amount is reconciled against the stored payment

付款結果通知帶有 `TradeAmt`。系統 MUST 在它與該筆付款紀錄的 `amount` 不一致時**拒絕推進**付款與訂單狀態，並以「請重送」的方式回應綠界，MUST NOT 靜默採信任一方的數字。

#### Scenario: 通知金額與紀錄不符時不推進
- **WHEN** 收到一個檢查碼正確、但 `TradeAmt` 與該筆付款紀錄 `amount` 不同的成功通知
- **THEN** 付款紀錄與訂單狀態皆不變，回應不是 `1|OK`

### Requirement: Simulated mode exercises the real wire shape without any external network

系統 MUST 提供一種模式，讓完整流程（發起付款 → 收銀台 → 付款結果通知 → 訂單轉為已付款）在**沒有綠界帳號、沒有外部網路**的情況下跑得通，且該模式下產生的欄位集與檢查碼 MUST 與正式模式**完全相同**——差異 MUST 僅在於收銀台網址這一個可設定值。

系統 MUST NOT 在任何測試或預設設定下呼叫綠界的正式或測試站網域。

模擬收銀台 MUST NOT 註冊為本 API router 上的路由。

#### Scenario: 收銀台網址是設定值
- **WHEN** 變更收銀台網址設定
- **THEN** 發起付款回傳的表單目標隨之改變，其餘欄位與檢查碼不受影響

#### Scenario: 模擬收銀台獨立於 API
- **WHEN** 列舉 API 的全部路由
- **THEN** 其中不存在任何模擬收銀台端點

#### Scenario: 模擬收銀台獨立驗證我們產生的檢查碼
- **WHEN** 模擬收銀台收到一組帶檢查碼的表單欄位
- **THEN** 它以設定的 HashKey/HashIV 重算並比對，不符時拒絕

### Requirement: ECPay credentials are resolved per shop, not from one platform-wide configuration

`ecpay` provider 的 `MerchantID`／`HashKey`／`HashIV`／`ChoosePayment` MUST 依 `InitiatePayment` 呼叫者提供的 `shopID`（發起付款）或 webhook URL 中的 shop id（驗證通知）解析，MUST NOT 有任何路徑讀取單一平台層共用設定作為憑證來源。尚未設定憑證的商家嘗試使用 `ecpay` provider 發起付款時，MUST 明確回報錯誤，MUST NOT 回退到平台範例憑證或任何其他商家已設定的憑證，MUST NOT 建立付款記錄或產生任何綠界欄位。

驗證通知時，MUST 使用 webhook URL 中 shop id 對應的商家憑證計算並比對 `CheckMacValue`；使用錯誤商家的憑證驗證屬於另一商家簽出的通知內容時，MUST 驗證失敗——兩個商家的密鑰互不相通，一個商家的 URL 不能被拿來驗證另一個商家的通知。

#### Scenario: 未設定憑證的商家無法以 ecpay 發起付款
- **WHEN** 商家尚未設定自己的 ECPay 憑證，卻對自己一張訂單以 `ecpay` provider 發起付款
- **THEN** 回報錯誤，不建立付款記錄，也不產生任何綠界欄位

#### Scenario: 兩個商家各自的簽章互不相通
- **WHEN** 以商家 A 的 `HashKey`/`HashIV` 對一組欄位計算出合法的 `CheckMacValue`，將整組欄位當作通知投遞到商家 B 的 webhook 路徑
- **THEN** 驗證失敗，不更新任何付款或訂單資料

#### Scenario: 商家各自的憑證各自生效
- **WHEN** 商家 A 與商家 B 分別設定了不同的 `MerchantID`，各自對自己一張訂單以 `ecpay` provider 發起付款
- **THEN** 兩者回傳的表單欄位集裡的 `MerchantID` 分別等於各自設定的值
