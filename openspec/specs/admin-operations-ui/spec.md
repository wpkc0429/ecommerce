# admin-operations-ui Specification

## Purpose
商家日常營運後台的行為契約：訂單的檢視、篩選與取消，出貨的建立與狀態推進，運送方式與會員等級的維護，會員點數的檢視與調整，以及自帶前端的接入設定（publishable key 與 allowed origin）。同時規範這些畫面的可見性如何由呼叫者的實際權限決定、金額／點數／百分比三種數值不得互相混用、以及深層連結的行為。

後台前端的交付形式（無建置步驟的靜態 ES module）與商品目錄的操作介面另見 spec `admin-catalog-ui`。
## Requirements
### Requirement: 後台提供商家日常營運的操作介面

平台的後台介面 SHALL 讓商家在不接觸 HTTP 客戶端或 JSON 的前提下，完成訂單、出貨、運送方式、會員等級、會員點數與前端接入設定的日常操作。

介面 MUST 只透過既有的公開 API（`/api/v1/admin/shops/{shopID}/...`）取得與寫入資料，MUST NOT 直接存取資料庫，也 MUST NOT 依賴任何未載於 `api/openapi/openapi.yaml` 的端點或欄位。

#### Scenario: 商家不需要 HTTP 客戶端即可完成一筆訂單的出貨

- **WHEN** 具備 `order.view` 與 `shipment.create` 的使用者在後台開啟一筆未出貨的訂單並填入物流商後送出
- **THEN** 出貨紀錄建立成功、訂單的出貨狀態更新為已出貨，且該使用者全程未撰寫任何 JSON 或 HTTP 請求

#### Scenario: 伺服器拒絕時原因對商家可見

- **WHEN** 任一操作被伺服器以 409 或 422 拒絕
- **THEN** 介面 MUST 顯示伺服器回傳的原因訊息，MUST NOT 只顯示通用失敗字樣或靜默無反應

### Requirement: 訂單列表支援分頁與伺服器端篩選，且篩選結果涵蓋整個訂單集合

訂單列表 SHALL 支援分頁，並 SHALL 支援依訂單狀態、付款狀態、出貨狀態、指定配送日區間與關鍵字篩選。

所有篩選 MUST 由伺服器執行（作為列表查詢的參數），MUST NOT 只對當前頁面的資料在前端過濾——分頁列表的前端過濾會對「符合條件但不在本頁」的訂單回報不存在，而漏掉一筆待出貨的訂單其後果不可回復。

#### Scenario: 篩選命中不在第一頁的訂單

- **WHEN** 商家以「未出貨」篩選訂單，而符合條件的訂單位於列表的第三頁
- **THEN** 該訂單 MUST 出現在篩選結果中

#### Scenario: 以指定配送日區間篩出當日待出貨的訂單

- **WHEN** 商家指定配送日區間為某一日，並同時篩選出貨狀態為未出貨
- **THEN** 結果 MUST 僅含該商家中指定配送日落在該日、且尚未出貨的訂單

#### Scenario: 日期篩選會排除未指定配送日的訂單，且介面必須說明

- **WHEN** 商家套用了任一指定配送日界限
- **THEN** 未填寫指定配送日的訂單 MUST NOT 出現在結果中，且介面 MUST 明示此一排除，MUST NOT 讓商家誤以為訂單已消失

#### Scenario: 以關鍵字尋找顧客的訂單

- **WHEN** 商家輸入收件人姓名或電話的一部分
- **THEN** 結果 MUST 含該商家中收件人姓名或電話包含該子字串的訂單（大小寫不敏感）

#### Scenario: 以訂單編號直接尋找

- **WHEN** 商家輸入一個訂單編號
- **THEN** 結果 MUST 含該編號的訂單（若存在於該商家）

### Requirement: 訂單詳情呈現金額三件組的組合關係

訂單詳情 SHALL 顯示品項小計、運費與應付總額，並 MUST 呈現三者的組合關係（品項小計 ＋ 運費 ＝ 應付總額），MUST NOT 只並列三個數值。

當訂單帶有等級折抵（`discount_amount > 0`）時，介面 MUST 額外呈現折抵項與其來源等級（等級名稱與當時套用的折扣率），且組合關係 MUST 顯示為「品項小計 − 折扣 ＋ 運費 ＝ 應付總額」。`discount_amount` 為 `0` 時 MUST NOT 顯示折抵項——每一筆訂單上都出現「− NT$0」會使商家學會忽略該列，而它恰恰是最需要被看見的一列。

訂單詳情 MUST 一併顯示每個品項的卡片訊息（若有）、收件資訊、指定配送日（若有）與運送方式名稱（若有）。

#### Scenario: 帶運費的訂單顯示可對帳的金額組合

- **WHEN** 一筆訂單的品項小計為 3,400、折抵為 0、運費為 150
- **THEN** 介面 MUST 顯示應付總額為 3,550，且 MUST 讓「3,550 由 3,400 ＋ 150 構成」對商家可見，MUST NOT 顯示折抵項

#### Scenario: 帶折扣的訂單顯示折抵與其來源等級

- **WHEN** 一筆訂單的品項小計為 3,400、折抵為 170（銀卡會員 5%）、運費為 150
- **THEN** 介面 MUST 顯示應付總額為 3,380，MUST 顯示折抵金額 170 與其來源等級名稱及百分比，且 MUST 讓「3,380 由 3,400 − 170 ＋ 150 構成」對商家可見

#### Scenario: 卡片訊息隨品項顯示

- **WHEN** 訂單中某一品項帶有卡片訊息
- **THEN** 該訊息 MUST 顯示在該品項所在的列，MUST NOT 顯示在訂單層級

### Requirement: 金額、點數與百分比在介面上不得互相混用

介面對金額的顯示與輸入 MUST 直接使用 API 的整數值，MUST NOT 乘以或除以任何倍率（延續 spec admin-catalog-ui 的不縮放規則）。

點數（會員餘額、點數異動量、等級門檻）MUST NOT 以任何貨幣格式呈現；百分比欄位（會員等級的折扣率、訂單上套用的折扣率）同理。點數與金額之間雖存在核發時的換算關係，介面 MUST NOT 讓兩者在顯示上難以分辨。

訂單詳情上同時出現的折抵**金額**與折扣**百分比** MUST 以各自的格式呈現，MUST NOT 互換——`10` 這個數字同時可以是 10% 與 NT$10，而兩者看起來都合理。

#### Scenario: 運費原值顯示

- **WHEN** 某運送方式的固定運費為 `150`、幣別為 TWD
- **THEN** 介面顯示的金額 MUST 表示 NT$150，MUST NOT 顯示為 1.5、15000 或任何其他被縮放的數值

#### Scenario: 點數不得顯示為金額

- **WHEN** 某會員的點數餘額為 `34`
- **THEN** 介面 MUST 以點數的形式呈現，MUST NOT 顯示為 NT$34 或任何貨幣格式

#### Scenario: 折扣率不得顯示為金額

- **WHEN** 一筆訂單的 `discount_percent` 為 `10`、`discount_amount` 為 `340`
- **THEN** 介面 MUST 將前者呈現為百分比、後者呈現為金額，MUST NOT 把 `10` 顯示為 NT$10 或把 `340` 顯示為 340%

### Requirement: 狀態變更只經由既有端點，且介面只提供伺服器接受的轉移

介面 MUST 只透過既有端點改變訂單與出貨的狀態，MUST NOT 以任何方式直接寫入狀態欄位。

出貨狀態的合法轉移只有「已出貨 → 已送達」與「已出貨 → 已退貨」，兩者皆為終態。介面 MUST 只在該筆出貨處於「已出貨」時提供這兩個操作，MUST NOT 提供任何伺服器保證會拒絕的轉移。

付款狀態由金流回呼推進，介面 MUST NOT 提供任何手動變更付款狀態的操作。

標記退貨的確認 MUST 說明其兩項後果：該訂單已核發的點數會被扣回（扣回的是整筆訂單的點數，即使該筆出貨只裝了一部分品項），且該訂單自此 MUST NOT 再建立新的出貨。

#### Scenario: 終態的出貨不再提供狀態按鈕

- **WHEN** 一筆出貨已標記為已送達或已退貨
- **THEN** 介面 MUST 只顯示其狀態與紀錄，MUST NOT 提供任何進一步的狀態變更操作

#### Scenario: 標記退貨前告知點數與後續出貨的後果

- **WHEN** 商家要將一筆出貨標記為退貨
- **THEN** 介面 MUST 在確認時說明該訂單已核發的點數會被扣回，且該訂單之後無法再建立出貨

#### Scenario: 已退貨的訂單不再提供建立出貨

- **WHEN** 一筆訂單已有出貨被標記為退貨，且仍有未出貨的品項
- **THEN** 介面 MUST NOT 提供建立新出貨的入口，並 MUST 說明原因

#### Scenario: 介面不提供手動標記付款

- **WHEN** 商家檢視一筆未付款的訂單
- **THEN** 介面 MUST 顯示其付款狀態與付款紀錄，MUST NOT 提供任何把它改為已付款的操作

### Requirement: 運送方式與會員等級可在後台維護

介面 SHALL 支援運送方式的列表、建立、編輯與刪除（名稱、物流商、固定運費、啟用旗標），以及會員等級的列表、建立、編輯與刪除（名稱、點數門檻、折扣百分比）。

會員等級畫面 MUST 說明折扣百分比會在結帳時自動套用於**商品金額**（運費不折），且變更 MUST 立即對其後建立的訂單生效、MUST NOT 影響既有訂單。介面 MUST NOT 呈現任何暗示折扣不會生效的說明。

#### Scenario: 建立運送方式後可被前台選用

- **WHEN** 商家建立一個啟用中的運送方式
- **THEN** 該方式 MUST 出現在後台列表，且 MUST 可在結帳時被選用

#### Scenario: 停用的運送方式仍可在後台檢視與編輯

- **WHEN** 某運送方式的啟用旗標為否
- **THEN** 它 MUST 仍出現在後台列表並可被編輯，MUST 與啟用中的方式在視覺上可分辨

#### Scenario: 會員等級畫面說明折扣的生效範圍

- **WHEN** 商家開啟會員等級的列表或編輯畫面
- **THEN** 畫面 MUST 說明折扣百分比套用於商品金額且運費不折，MUST NOT 出現「本階段僅儲存」「不套用」之類的說明

### Requirement: 會員點數餘額、流水帳與手動調整

介面 SHALL 以會員為單位顯示其點數餘額、目前等級與點數流水帳（分頁），流水帳 MUST 顯示每一筆的異動量、種類、關聯訂單（若有）與時間。

具備 `point.adjust` 的使用者 SHALL 能對該會員手動調整點數，MUST 同時填寫非零的異動量與非空的理由。

**點數的手動調整與流水帳 MUST 只存在於這一個視圖。** 其他視圖（例如顧客詳情）MAY 顯示唯讀的餘額與等級並提供連往本視圖的入口，但 MUST NOT 內嵌調整表單或流水帳——一份餘額在兩個畫面上各自維護會漂移，而點數的稽核軌跡 MUST 只有一條寫入路徑。

#### Scenario: 訂單付款後的核發在後台可見

- **WHEN** 某會員的訂單付款成功而系統核發了點數
- **THEN** 該會員的餘額 MUST 反映核發結果，且流水帳 MUST 含一筆帶該訂單編號的核發紀錄

#### Scenario: 無調整權限者看不到調整入口

- **WHEN** 使用者具備 `point.view` 但不具備 `point.adjust`
- **THEN** 介面 MUST 顯示餘額與流水帳，MUST NOT 顯示任何手動調整的入口

#### Scenario: 其他視圖不得內嵌點數調整

- **WHEN** 另一個視圖需要呈現某位顧客的點數
- **THEN** 它 MUST 只顯示唯讀的餘額與等級並提供連往點數視圖的入口，MUST NOT 內嵌調整表單或流水帳

### Requirement: 前端接入設定：publishable key 為商家層，allowed origin 為平台層

介面 SHALL 支援 publishable key 的列出、產生與撤銷，以及 allowed origin 的列出、登記與移除。

這兩者的權限層級不同：publishable key 由商家層權限（`publishable_key.*`）決定，allowed origin 由平台層權限（`shop.manage_client_origins`）決定。介面 MUST 依呼叫者的實際有效權限分別決定兩個區塊的可見性，MUST NOT 以其中一者的權限推論另一者。

已撤銷的 key MUST 仍出現在列表中並標示其撤銷時間——「哪一把金鑰在什麼時候被切斷」正是軟刪除要回答的問題。

#### Scenario: 商家 owner 看得到金鑰區塊但看不到 origin 區塊

- **WHEN** 僅具商家層權限的使用者開啟前端接入設定
- **THEN** publishable key 區塊 MUST 可見且可操作，allowed origin 區塊 MUST NOT 出現

#### Scenario: 具平台層權限者兩個區塊都看得到

- **WHEN** 具備 `shop.manage_client_origins` 的使用者開啟同一畫面
- **THEN** 兩個區塊 MUST 皆可見且可操作

#### Scenario: 產生的金鑰以完整值顯示

- **WHEN** 商家產生一把新的 publishable key
- **THEN** 介面 MUST 顯示其完整值（它是公開識別碼而非憑證），MUST NOT 遮蔽

### Requirement: 介面依呼叫者的實際權限決定可見與可操作

每一個視圖與每一個會改變資料的操作 MUST 依呼叫者在當前商家的**實際有效權限**決定是否呈現：缺少檢視權限的視圖 MUST NOT 出現在導覽；缺少建立／編輯／刪除權限的對應操作 MUST NOT 呈現為可用的入口。

有效權限的來源 MUST 是伺服器判定後的結果，MUST NOT 由前端依角色名稱或任何本地規則推論。切換商家後 MUST 重新取得。

此機制是體驗層，MUST NOT 被視為安全邊界——伺服器端的授權判定 MUST 維持為唯一權威。

#### Scenario: 只具檢視權限者看不到破壞性操作

- **WHEN** 使用者具備 `order.view` 但不具備 `order.cancel`
- **THEN** 訂單畫面 MUST 可檢視，取消訂單的入口 MUST NOT 出現

#### Scenario: 完全無相關權限者不會看到該分頁

- **WHEN** 使用者不具備 `shipping_method.view`
- **THEN** 運送方式分頁 MUST NOT 出現在導覽

### Requirement: 後台視圖具備可分享的深層連結

後台 SHALL 讓每一個視圖、以及訂單詳情、會員點數與顧客詳情這三個帶參數的視圖，具有可貼給他人的連結；開啟該連結 MUST 直接抵達對應畫面。

指向呼叫者無權檢視之視圖的連結，或指向不存在之視圖的連結，MUST 回落到一個該呼叫者有權進入的畫面，MUST NOT 呈現為錯誤或空白畫面。

篩選條件與搜尋關鍵字 MUST NOT 成為連結的一部分——深層連結要解決的是「這一筆」，不是「這個查詢」。

#### Scenario: 訂單詳情的連結可直接開啟

- **WHEN** 使用者開啟一個指向特定訂單詳情的後台連結
- **THEN** 該訂單的詳情 MUST 直接顯示，MUST NOT 需要先經過列表再點選

#### Scenario: 顧客詳情的連結可直接開啟

- **WHEN** 使用者開啟一個指向特定顧客詳情的後台連結
- **THEN** 該顧客的詳情 MUST 直接顯示，MUST NOT 需要先經過名冊再搜尋

#### Scenario: 無權限的深層連結安全回落

- **WHEN** 使用者開啟一個指向自己無權檢視之視圖的連結
- **THEN** 介面 MUST 落到一個該使用者有權進入的畫面，MUST NOT 顯示空白或錯誤

### Requirement: 商家營運的關鍵操作路徑由瀏覽器 E2E 覆蓋

營運後台的關鍵路徑 SHALL 由真實瀏覽器的端對端測試覆蓋，且該測試 MUST 屬於既有的單一 E2E 入口，MUST NOT 是一個需要另外被告知才會執行的獨立入口。

覆蓋範圍 MUST 至少包含：於後台建立運送方式、以該運送方式完成一筆前台下單、於後台訂單詳情看到該筆訂單、建立出貨並推進其狀態、**於後台以品項層級只出貨其中一部分並看到訂單狀態與已出貨數量如實更新**、於後台看到該顧客的點數餘額與流水帳、以及產生一把 publishable key。

#### Scenario: 端對端鏈路可驗證

- **WHEN** 執行既有的 E2E 入口
- **THEN** 上述路徑 MUST 全數被實際執行並斷言，任一環節失敗 MUST 使整體結果為失敗

#### Scenario: 權限層級差異被機械化鎖住

- **WHEN** 以僅具商家層權限的身分查詢自己的有效權限
- **THEN** 測試 MUST 斷言結果含 publishable key 的權限節點且不含 `shop.manage_client_origins`，並斷言其對 allowed origin 端點的請求被拒絕

### Requirement: 出貨介面支援品項層級的部分出貨，並如實呈現已出貨與未出數量

出貨的粒度是**訂單品項**：一筆訂單 MAY 有多筆出貨紀錄。介面 MUST 在建立出貨時提供品項層級的數量輸入，每一列的預設值 MUST 為該品項尚未出貨的數量，且 MUST NOT 允許送出超過該數量的值。

訂單品項表格 MUST 呈現每個品項的「已出貨數量／訂購數量」。該數字 MUST 取自伺服器回傳的訂單品項欄位，MUST NOT 由介面自行加總出貨紀錄推導——後者會在多筆出貨下與伺服器的權威值漂移，且它是伺服器上並發防護所依據的同一個數字。

介面 MUST 明示「省略品項＝出貨全部未出品項」這個既有行為的存在（一次出完仍然是一個操作，而不是必須逐項勾選）。

出貨成功後，介面 MUST 重新向伺服器取得訂單與出貨紀錄，MUST NOT 以本地計算的結果更新畫面。

#### Scenario: 部分出貨表單以未出數量為預設值與上限

- **WHEN** 商家開啟一筆含兩個品項（各訂購 2 件、其中一項已出 1 件）的訂單的出貨表單
- **THEN** 表單 MUST 逐項列出品項與可出數量，該已出 1 件的品項預設與上限 MUST 為 1，另一項 MUST 為 2

#### Scenario: 品項表格呈現已出貨數量

- **WHEN** 商家檢視一筆已部分出貨的訂單
- **THEN** 每個品項 MUST 顯示其已出貨數量與訂購數量，且該值來自伺服器的訂單回應

#### Scenario: 一次出完仍是單一操作

- **WHEN** 商家對一筆從未出貨的訂單選擇整筆出貨
- **THEN** 介面 MUST 以一個操作完成，MUST NOT 要求逐項確認數量

### Requirement: 一筆訂單的多筆出貨在後台以清單呈現，各自可獨立推進狀態

介面 MUST 以清單呈現一筆訂單的所有出貨紀錄，每一筆 MUST 顯示其物流商、追蹤號、狀態、時間與**該筆所裝載的品項與數量**。

每一筆出貨的狀態操作 MUST 各自獨立判定：只有處於「已出貨」的那些出貨紀錄才提供「標記已送達／標記退貨」，終態的出貨 MUST NOT 提供任何狀態操作。

訂單層的出貨狀態徽章 MUST 能表達「部分出貨」，MUST NOT 把部分出貨顯示為已出貨。

#### Scenario: 多筆出貨各自呈現與操作

- **WHEN** 一筆訂單有兩筆出貨，其一已送達、其一仍在運送中
- **THEN** 介面 MUST 同時列出兩筆及其各自裝載的品項；已送達的那筆 MUST NOT 有狀態按鈕，運送中的那筆 MUST 有兩顆終態按鈕

#### Scenario: 部分出貨的訂單狀態如實顯示

- **WHEN** 商家檢視一筆只出了部分品項的訂單
- **THEN** 訂單的出貨狀態 MUST 顯示為「部分出貨」，MUST NOT 顯示為「已出貨」
