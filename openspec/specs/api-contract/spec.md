# api-contract Specification

## Purpose

`/api/v1` 的**介面契約**（`api/openapi/openapi.yaml`）本身的行為契約。它與 `openspec/specs/` 的其餘能力不重疊：那些回答「這個行為對不對」，這一份回答「這個契約憑什麼可以被相信」。

前提是一份與實作不符的 API 文件**比沒有文件更危險**——消費端會照著它寫。因此本能力規範的不是「要寫文件」，而是覆蓋範圍的完整性、金額單位的單一聲明、與實作一致性的自動驗證、以及 D13「v1 只做 additive 變更」的機械化強制，全部必須由持續整合流程執行，不得倚賴開發者記得。

## Requirements
### Requirement: 機讀 API 契約涵蓋整個公開 API 表面

系統 MUST 維護一份機讀的 API 契約文件，涵蓋伺服器實際註冊的**每一條**公開路由——包含後台（`/api/v1/admin/**`）、前台（`/api/v1/shop/**`）、訪客路徑、金流回呼（`/api/v1/webhooks/**`）、渲染端點（`/api/v1/render/**`）與健康檢查。

該文件 MUST 為 OpenAPI 3.1 格式（其 schema 即 JSON Schema 2020-12，因此可被既有的 schema 驗證器直接消費），MUST 存放於版本控制中，且 MUST 可在不啟動任何服務、不連接資料庫的情況下被獨立閱讀與工具消費。

該文件 MUST NOT 由伺服器在執行期讀取，MUST NOT 參與任何 request 驗證或授權判定。

#### Scenario: 契約涵蓋每一條註冊路由

- **WHEN** 走訪伺服器組裝完成的路由表
- **THEN** 每一條「HTTP 方法 ＋ 路徑樣板」的組合都在契約文件中有對應的定義

#### Scenario: 契約可離線獨立消費

- **WHEN** 只取得契約文件本身（不取得本 repo 的其餘部分、不啟動任何服務）
- **THEN** 該文件足以產生一個可回應的 mock server，且其回應的資料形狀與真實 API 相同

### Requirement: 路由覆蓋由自動化檢查雙向強制，且該檢查在 CI 內執行

系統 MUST 具備一項自動化檢查，比對「伺服器實際註冊的路由集合」與「契約文件宣告的路由集合」，並 MUST 於**兩個方向**皆不相等時失敗：

- 實作有而契約沒有（新增端點未記載）MUST 失敗；
- 契約有而實作沒有（幽靈端點，呼叫端照做會得到 404）MUST 失敗。

該檢查 MUST 由持續整合流程自動執行，MUST NOT 僅依賴開發者手動觸發。該檢查 MUST NOT 需要資料庫、快取或任何外部基礎設施。

檢查失敗時 MUST 明確列出兩個方向各自缺少哪些路由。

**路由集合的來源**：該檢查所走訪的路由表 MUST 由 HTTP 層相依結構（`Deps`）**機械推導**而得——系統 MUST 逐欄位填滿該結構後組裝 router，MUST NOT 以人工維護的相依清單作為來源。新增一個相依欄位 MUST 在無人修改該檢查的前提下自動被納入。

填充過程中，任一欄位若其型別無法以機械方式產生非 nil 值，系統 MUST 明確失敗並指名該欄位與其型別，MUST NOT 靜默略過使其維持 nil——靜默略過會讓該欄位所控制的整組路由自檢查中消失，正是本來源要求所要消除的失效模式。

**與生產路由表的等價性**：系統 MUST 另具備一項自動化檢查，以真實的應用程式組裝流程（服務啟動時所用的同一段程式碼）建立 router，並斷言其路由表與上述覆蓋檢查所走訪的路由表**逐條相同**。此檢查 MAY 需要基礎設施，且 MUST 由持續整合流程執行。

#### Scenario: 新增端點未同步契約

- **WHEN** 實作新增一條路由，契約文件未同步更新
- **THEN** 自動化檢查失敗，並指出該路由存在於實作但不存在於契約

#### Scenario: 新增相依而未更新任何檢查程式碼

- **WHEN** 實作在 HTTP 層相依結構中新增一個 handler 欄位、掛上其路由，且未修改路由覆蓋檢查的任何一行
- **THEN** 該路由仍被列舉；若契約文件未同步宣告它，路由覆蓋檢查失敗

#### Scenario: 相依型別無法機械填充

- **WHEN** HTTP 層相依結構新增一個無法由機械規則產生非 nil 值的欄位（例如介面型別）
- **THEN** 路由覆蓋檢查失敗並指名該欄位與其型別，要求明示登記一個值

#### Scenario: 檢查來源與生產組裝出的路由表不一致

- **WHEN** 路由掛載條件改為依賴相依欄位是否為 nil 以外的判準，使檢查所走訪的路由表與真實服務啟動後的路由表產生差異
- **THEN** 等價性檢查失敗，並列出兩者相差的路由

#### Scenario: 契約保留已被移除的端點

- **WHEN** 實作移除一條路由，契約文件仍宣告它
- **THEN** 自動化檢查失敗，並指出該路由存在於契約但不存在於實作

#### Scenario: 路徑參數改名

- **WHEN** 實作將某路由的路徑參數改名（例如 `{orderID}` → `{id}`）
- **THEN** 自動化檢查失敗（兩個方向各多出一條不相符的路徑）

#### Scenario: 檢查不需要基礎設施

- **WHEN** 在沒有資料庫與快取的環境執行單元測試
- **THEN** 路由覆蓋檢查仍然執行並產出結果（不被跳過）

### Requirement: 真實回應以契約中的 schema 驗證

系統 MUST 具備一項自動化檢查，對真實的伺服器路由發出真實請求，並以契約文件中的對應 schema 驗證回應主體。

該檢查 MUST 涵蓋：自帶前端完成「列商品 → 選運送方式 → 訪客結帳 → 付款 → 查訂單 → 查出貨」這條路徑所需的每一條端點；每一個被多條端點共用的資料結構至少一次；以及統一錯誤 envelope 的未認證、不存在、與驗證失敗三種形態各至少一次。

驗證失敗時 MUST 指出不符之處位於回應中的哪個位置。

#### Scenario: 回應新增未記載的鍵

- **WHEN** 實作在某個共用資料結構的回應中新增一個鍵，契約未同步
- **THEN** 回應驗證檢查失敗（該 schema 不允許未宣告的額外屬性）

#### Scenario: 回應移除已記載的鍵

- **WHEN** 實作移除某個回應鍵，契約仍宣告它為必要
- **THEN** 回應驗證檢查失敗

#### Scenario: 回應欄位型別改變

- **WHEN** 實作把某個整數欄位改為字串輸出
- **THEN** 回應驗證檢查失敗

#### Scenario: 驗證失敗回應的結構受契約約束

- **WHEN** 以刻意不合法的輸入呼叫端點而取得 422
- **THEN** 該回應符合契約的錯誤 envelope schema，且其 `details` 為 JSON Pointer 陣列

### Requirement: 金額欄位共用單一單位定義，且新增金額欄位不得省略聲明

契約中所有表示貨幣金額的欄位 MUST 引用**同一個**共用的金額型別定義，該定義 MUST 明確聲明「整數、最小貨幣單位、非浮點數、幣別由同層的 `currency` 決定」。

系統 MUST 具備一項自動化檢查，走訪契約文件的全部 schema，凡屬性名稱屬於金額語意者，MUST 驗證其為對該共用金額型別的引用，MUST NOT 允許就地展開為匿名的數值型別。

契約文件提供的範例值 MUST 使用真實量級（與示範資料一致），MUST NOT 使用會誤導單位的簡化值。

#### Scenario: 新增金額欄位而未引用共用定義

- **WHEN** 契約新增一個金額語意的屬性，但就地寫成匿名的整數型別
- **THEN** 金額單位紀律檢查失敗，並指出該屬性的位置

#### Scenario: 單位聲明只需維護一處

- **WHEN** 金額單位的敘述需要修改
- **THEN** 只需修改共用金額型別的定義一處，所有引用它的欄位同時更新

### Requirement: v1 表面受鎖檔保護，移除任何公開承諾必須是明示動作

系統 MUST 維護一份版本控制中的 v1 表面鎖檔，記錄 v1 已對外承諾的每一項可機械列舉的公開事實，至少涵蓋：

- **每一條路由**（HTTP 方法 ＋ 路徑樣板）；
- **每一個具名資料結構的公開回應鍵**；
- **每一條端點所接受的每一個請求參數**，記錄其名稱、所在位置（標頭／查詢字串／路徑）、以及**是否可以省略**；
- **每一條端點所承諾回應的標頭**（含其所屬狀態碼）。

請求參數與回應標頭 MUST 以**端點為單位**記錄，MUST NOT 僅以契約文件中的可重用元件為單位記錄——消費端依賴的承諾是「這條端點接受該參數」，而非「文件中存在某個可重用元件」。因此，將某條端點對共用參數元件的引用移除、而保留元件定義本身，MUST 導致檢查失敗。

鎖檔 MUST 同時涵蓋以共用元件表達與就地展開表達的參數與回應標頭；解析共用元件引用時，若引用無法解析，系統 MUST 失敗並指出該引用，MUST NOT 靜默略過（否則重新產生鎖檔時會安靜地產出一份不完整的鎖）。

系統 MUST 具備一項自動化檢查，驗證鎖檔中的**每一行**在契約文件中仍然存在。新增路由、欄位、參數或回應標頭 MUST NOT 導致該檢查失敗（additive 變更自由）；移除任何一項 MUST 導致該檢查失敗。

**必填方向性**：將某個請求參數由選填改為必填 MUST 導致檢查失敗（收緊 ＝ 破壞性）；由必填改為選填 MUST NOT 導致檢查失敗（放寬 ＝ additive）。此方向性 MUST 由鎖檔所記錄的事實本身表達，MUST NOT 藉由讓檢查邏輯對不同種類的行套用不同比較規則來達成——檢查的判定規則 MUST 維持為單一且可由人在審查時原地驗證的形式（「鎖檔的每一行今天仍存在於契約中」）。

**粒度邊界**：鎖檔 MUST NOT 記錄參數的型別、格式、長度或值域約束、敘述文字與範例值。修改參數的敘述、補充範例、或放寬其值域約束 MUST NOT 導致檢查失敗。此邊界為刻意取捨：系統 MUST NOT 宣稱鎖檔能擋住約束的收緊，該部分的防線是變更審查而非本檢查。

修復該失敗的唯一方式 MUST 是人工從鎖檔中刪除對應行——該刪除動作 MUST 在版本控制的差異中可見且可審查。

鎖檔 MUST NOT 依賴 git 歷史或任何滑動的比較基準點。

檢查失敗時 MUST 逐項列出消失的行，且該行 MUST 足以指出是哪一條端點的哪一個承諾。

#### Scenario: 純新增不觸發失敗

- **WHEN** 契約新增一條路由與若干新回應鍵，且未移除任何既有項目
- **THEN** 表面鎖檢查通過

#### Scenario: 靜默移除公開回應鍵

- **WHEN** 契約移除一個已在鎖檔中的公開回應鍵
- **THEN** 表面鎖檢查失敗，並指出缺少的那一項

#### Scenario: 靜默移除請求標頭參數

- **WHEN** 契約從某條端點移除一個已在鎖檔中的請求標頭參數
- **THEN** 表面鎖檢查失敗，並指出是哪一條端點的哪一個標頭消失了

#### Scenario: 選填參數被改成必填

- **WHEN** 契約將某個原本可省略的請求參數改為必填
- **THEN** 表面鎖檢查失敗，並指出該端點的該參數不再可省略

#### Scenario: 必填參數被放寬為選填

- **WHEN** 契約將某個原本必填的請求參數改為選填，且未移除任何參數
- **THEN** 表面鎖檢查通過（放寬是 additive 變更）

#### Scenario: 移除端點對共用參數元件的引用

- **WHEN** 契約從某條端點刪除對共用參數元件的引用，但保留該元件的定義
- **THEN** 表面鎖檢查失敗（承諾是以端點為單位做出的）

#### Scenario: 移除已承諾的回應標頭

- **WHEN** 契約移除某條端點在某個狀態碼下承諾的回應標頭
- **THEN** 表面鎖檢查失敗，並指出該端點、該狀態碼與該標頭

#### Scenario: 無害的敘述修改不觸發失敗

- **WHEN** 契約只修改某個請求參數的敘述文字或範例值，未改變其名稱、位置與是否必填
- **THEN** 表面鎖檢查通過

#### Scenario: 共用元件引用無法解析

- **WHEN** 契約中某個參數或回應的共用元件引用指向不存在的元件
- **THEN** 檢查失敗並指出該引用，而非把該項目視為不存在

#### Scenario: 破壞 v1 必須留下可審查的痕跡

- **WHEN** 開發者確實需要移除一個 v1 的公開承諾
- **THEN** 除了修改契約，還必須從鎖檔刪除對應行，該刪除出現在程式碼審查的差異中

### Requirement: 統一錯誤格式與認證機制在契約中各表達一次並共用

契約 MUST 將統一錯誤 envelope 表達為單一共用定義，並由各端點以引用方式使用，MUST NOT 在每個端點重複展開。

契約 MUST 能區分系統中彼此互斥的認證機制（後台 JWT、會員 JWT、訂單存取 token、金流簽章），並 MUST 為每一種說明其受眾限制與失敗行為。

訂單存取 token 的說明 MUST 明確指出它不是 session：它只能存取它指名的那一筆訂單，其路由不接受路徑上的訂單識別碼，且不能用於列出訂單歷史、取消訂單或換發。

publishable key MUST NOT 被表達為認證機制。它 MUST 被表達為決定租戶的識別碼，並 MUST 明確說明它是公開值、不參與授權判定、無效時回 404 且不回退至其他解析方式。

契約 MUST 說明「任何端點皆可能回傳未預期的伺服器錯誤」與「受速率限制的端點可能回傳限流錯誤」，端點層級 MUST 只列出呼叫端需要分辨並採取不同動作的狀態碼。

#### Scenario: 錯誤格式集中定義

- **WHEN** 需要修改錯誤 envelope 的描述或結構
- **THEN** 只需修改契約中的單一共用定義，所有引用它的端點同時更新

#### Scenario: publishable key 不被描述為憑證

- **WHEN** 閱讀契約中的安全機制章節
- **THEN** publishable key 不出現在其中；它出現在請求標頭參數的定義中，並註明是識別碼而非憑證

#### Scenario: 訂單存取 token 的邊界明確

- **WHEN** 閱讀訂單存取 token 的說明
- **THEN** 該說明指出它只能觸及單一訂單、其路由不接受訂單識別碼、且不能列訂單歷史／取消／換發

### Requirement: 自帶前端接入說明為單一權威文件

系統 MUST 提供一份給自帶前端（非平台託管的靜態站、SPA 或原生應用）的接入說明文件，MUST 存放於版本控制中的活文件位置，MUST NOT 以已封存的變更紀錄作為接入資訊的來源。

該文件 MUST 依實際接入流程組織（取得識別與 origin → 讀商品 → 讀運送方式 → 下單 → 付款 → 查單 → 身分認領），每一步 MUST 提供可直接照做的請求範例。

該文件 MUST 在開頭聲明金額為最小貨幣單位整數。該文件 MUST NOT 重複列舉完整欄位表（欄位以機讀契約為準），且 MUST 對讀者聲明此分工。

該文件 MUST 包含錯誤對照表，將狀態碼、錯誤代碼與驗證失敗指標對應到具體意義與處置。

#### Scenario: 接入資訊有單一來源

- **WHEN** 外部前端開發者需要知道如何完成訪客結帳
- **THEN** 只需閱讀該接入說明文件，無需拼接多份已封存的變更紀錄

#### Scenario: 金額單位在最顯眼處聲明

- **WHEN** 開發者開始閱讀該接入說明文件
- **THEN** 在進入任何端點說明之前就已讀到「金額為最小貨幣單位整數」的聲明

### Requirement: 契約與實作不一致時以實作為權威

當自動化檢查揭露契約與實作不一致時，系統的處置順序 MUST 為：既有的行為驗收 spec 優先於實作，實作優先於契約文件。

因此，除非檢查揭露的是實作違反了既有行為驗收 spec，否則 MUST 修改契約文件使其符合實作，MUST NOT 為了遷就契約而改變已通過行為驗收的實作。

契約文件 MUST NOT 成為執行期的第二權威：它 MUST NOT 被用於 request 驗證、回應過濾或授權判定。

#### Scenario: 實作正確而契約過時

- **WHEN** 自動化檢查失敗，且實作的行為符合既有行為驗收 spec
- **THEN** 修改契約文件使其符合實作

#### Scenario: 實作違反既有行為驗收

- **WHEN** 自動化檢查失敗，且檢查揭露的是實作違反了既有行為驗收 spec
- **THEN** 修改實作，契約文件維持原樣
