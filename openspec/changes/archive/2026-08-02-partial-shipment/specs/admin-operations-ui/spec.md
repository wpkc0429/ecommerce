## ADDED Requirements

### Requirement: 出貨介面支援品項層級的部分出貨，並如實呈現已出貨與未出數量

出貨的粒度是**訂單品項**：一筆訂單 MAY 有多筆出貨紀錄。介面 MUST 在建立出貨時提供品項層級的數量輸入，每一列的預設值 MUST 為該品項尚未出貨的數量，且 MUST NOT 允許送出超過該數量的值。

訂單品項表格 MUST 呈現每個品項的「已出貨數量／訂購數量」。該數字 MUST 取自伺服器回傳的訂單品項欄位，MUST NOT 由介面自行加總出貨紀錄推導——後者會在多筆出貨下與伺服器的權威值漂移，且它是伺服器上並發防護所依據的同一個數字。

介面 MUST 明示「省略品項＝出貨全部未出品項」這個既有行為的存在（一次出完仍然是一個操作，而不是必須逐項勾選）。

出貨成功後，介面 MUST 重新向伺服器取得訂單與出貨紀錄，MUST NOT 以本地計算的結果更新畫面。

#### Scenario: 部分出貨表單以未出數量為預設值與上限

- **WHEN** 商家開啟一筆含兩個品項（各訂購 2 件、其中一項已出 1 件）的訂單的出貨表單
- **THEN** 表單 MUST 逐項列出品項與可出數量，該已出 1 件的品項預設與上限 MUST 為 1，另一項 MUST 為 2

#### Scenario: 品項表格呈現已出貨數量

- **WHEN** 商家檢視一筆已部分出貨的訂單
- **THEN** 每個品項 MUST 顯示其已出貨數量與訂購數量，且該值來自伺服器的訂單回應

#### Scenario: 一次出完仍是單一操作

- **WHEN** 商家對一筆從未出貨的訂單選擇整筆出貨
- **THEN** 介面 MUST 以一個操作完成，MUST NOT 要求逐項確認數量

### Requirement: 一筆訂單的多筆出貨在後台以清單呈現，各自可獨立推進狀態

介面 MUST 以清單呈現一筆訂單的所有出貨紀錄，每一筆 MUST 顯示其物流商、追蹤號、狀態、時間與**該筆所裝載的品項與數量**。

每一筆出貨的狀態操作 MUST 各自獨立判定：只有處於「已出貨」的那些出貨紀錄才提供「標記已送達／標記退貨」，終態的出貨 MUST NOT 提供任何狀態操作。

訂單層的出貨狀態徽章 MUST 能表達「部分出貨」，MUST NOT 把部分出貨顯示為已出貨。

#### Scenario: 多筆出貨各自呈現與操作

- **WHEN** 一筆訂單有兩筆出貨，其一已送達、其一仍在運送中
- **THEN** 介面 MUST 同時列出兩筆及其各自裝載的品項；已送達的那筆 MUST NOT 有狀態按鈕，運送中的那筆 MUST 有兩顆終態按鈕

#### Scenario: 部分出貨的訂單狀態如實顯示

- **WHEN** 商家檢視一筆只出了部分品項的訂單
- **THEN** 訂單的出貨狀態 MUST 顯示為「部分出貨」，MUST NOT 顯示為「已出貨」

## MODIFIED Requirements

### Requirement: 狀態變更只經由既有端點，且介面只提供伺服器接受的轉移

介面 MUST 只透過既有端點改變訂單與出貨的狀態，MUST NOT 以任何方式直接寫入狀態欄位。

出貨狀態的合法轉移只有「已出貨 → 已送達」與「已出貨 → 已退貨」，兩者皆為終態。介面 MUST 只在該筆出貨處於「已出貨」時提供這兩個操作，MUST NOT 提供任何伺服器保證會拒絕的轉移。

付款狀態由金流回呼推進，介面 MUST NOT 提供任何手動變更付款狀態的操作。

標記退貨的確認 MUST 說明其兩項後果：該訂單已核發的點數會被扣回（扣回的是整筆訂單的點數，即使該筆出貨只裝了一部分品項），且該訂單自此 MUST NOT 再建立新的出貨。

#### Scenario: 終態的出貨不再提供狀態按鈕

- **WHEN** 一筆出貨已標記為已送達或已退貨
- **THEN** 介面 MUST 只顯示其狀態與紀錄，MUST NOT 提供任何進一步的狀態變更操作

#### Scenario: 標記退貨前告知點數與後續出貨的後果

- **WHEN** 商家要將一筆出貨標記為退貨
- **THEN** 介面 MUST 在確認時說明該訂單已核發的點數會被扣回，且該訂單之後無法再建立出貨

#### Scenario: 已退貨的訂單不再提供建立出貨

- **WHEN** 一筆訂單已有出貨被標記為退貨，且仍有未出貨的品項
- **THEN** 介面 MUST NOT 提供建立新出貨的入口，並 MUST 說明原因

#### Scenario: 介面不提供手動標記付款

- **WHEN** 商家檢視一筆未付款的訂單
- **THEN** 介面 MUST 顯示其付款狀態與付款紀錄，MUST NOT 提供任何把它改為已付款的操作

### Requirement: 商家營運的關鍵操作路徑由瀏覽器 E2E 覆蓋

營運後台的關鍵路徑 SHALL 由真實瀏覽器的端對端測試覆蓋，且該測試 MUST 屬於既有的單一 E2E 入口，MUST NOT 是一個需要另外被告知才會執行的獨立入口。

覆蓋範圍 MUST 至少包含：於後台建立運送方式、以該運送方式完成一筆前台下單、於後台訂單詳情看到該筆訂單、建立出貨並推進其狀態、**於後台以品項層級只出貨其中一部分並看到訂單狀態與已出貨數量如實更新**、於後台看到該顧客的點數餘額與流水帳、以及產生一把 publishable key。

#### Scenario: 端對端鏈路可驗證

- **WHEN** 執行既有的 E2E 入口
- **THEN** 上述路徑 MUST 全數被實際執行並斷言，任一環節失敗 MUST 使整體結果為失敗

#### Scenario: 權限層級差異被機械化鎖住

- **WHEN** 以僅具商家層權限的身分查詢自己的有效權限
- **THEN** 測試 MUST 斷言結果含 publishable key 的權限節點且不含 `shop.manage_client_origins`，並斷言其對 allowed origin 端點的請求被拒絕

## REMOVED Requirements

### Requirement: 出貨介面如實呈現「整筆訂單、至多一筆出貨」的語意

**Reason**: 該禁令的理由是明文寫下的「該概念在系統中沒有對應的資料」——本 change 建立了那份資料（`shipment_items` 與訂單品項的已出貨數量），前提消失，禁令跟著到期。它被上方兩條 ADDED 需求取代：介面現在 MUST 提供品項層級的數量輸入，並 MUST 呈現已出貨／訂購數量。

**Migration**: 後台訂單詳情的出貨區塊改為「多筆出貨清單 ＋ 品項層級出貨表單」。既有的「一次全出」操作不消失，它對應到 API 上省略品項清單的請求，因此既有的整筆出貨行為與斷言完全保留。
