## Context

本 API 目前有兩條建立訂單的入口，兩者的重複送出防護完全不對稱：

```
POST /api/v1/shop/checkout        會員：品項來自伺服器端購物車
    → 第二次呼叫時 cart 已是 Converted → 409「cart has already been checked out」

POST /api/v1/shop/guest/checkout  訪客：品項由請求自帶
    → 每次都是一次完整、獨立、可重入的建單 → 兩筆訂單，各自正確扣庫存
```

會員路徑的 409 不是冪等，是**衝突**：它告訴客戶端「這台購物車已經結過帳了」，但**不告訴它訂單是哪一筆**。在「請求送出、回應遺失」這個情境下，客戶端拿到 409 之後仍然不知道自己的訂單成不成立——它只知道有人結過這台車的帳（很可能就是它自己）。這是本變更要修的第二個缺口，也是「會員路徑要不要一起做」這個問題的真正答案（D10）。

`order.Service.Checkout` 是全系統並發安全性最集中的一段程式：單一 `ent.Tx` 內先以 CAS 把 cart 由 Active 翻成 Converted，再逐行以 `UPDATE ... WHERE stock_qty >= ?` 條件式扣庫存並檢查受影響列數。它由三個 `-race` 測試守著（`TestCheckoutConcurrentOversellingProtection`、`TestGuestCheckoutConcurrentOversellingProtection`、`TestGuestAndMemberCheckoutShareOneStockGuard`）。**本變更所有新邏輯都必須落在扣庫存迴圈之外**，且必須以那三個測試一行不改地通過作為「未被削弱」的證據。

本專案既有的三種冪等／並發仲裁模式，本設計沿用而非另創：

| 出處 | 機制 | 仲裁者 |
| --- | --- | --- |
| `payment-integration` | webhook 的 CAS：`UPDATE ... WHERE status = pending` + 受影響列數 | 條件式 UPDATE |
| `member-tiers-and-points` | `point_transactions(order_id, kind)` UNIQUE | 資料庫唯一索引 |
| `order-management` | 條件式扣庫存 + 受影響列數 | 條件式 UPDATE |

三者的共同紀律是**最終仲裁者是資料庫，不是應用層的 read-then-write**。本變更的 key 預約沿用中間那一條（唯一索引），完成／釋放沿用前後兩條（條件式 UPDATE + 受影響列數）。

消費端的既有形狀（`bouquet/public/app.js`，本變更不碰該 repo）：

```js
resetCheckout() → state.submit.key = 'k-' + Date.now().toString(36) + '-' + rand   // 進入結帳時產生
submitOrder()  → body.key = state.submit.key;  15s AbortController 逾時
handleSubmitResponse(key, status, data):
  201            → 清空購物車、顯示訂單編號
  400 欄位錯誤   → state.submit.key = key（**保留同一把 key**），讓顧客改欄位再送
  409 價格改變   → 保留 key，顯示新價格要顧客再確認
  0 / 5xx        → status='error'，送出鈕文案變成「重新送出」，重送同一把 key
```

這段程式碼已經存在、已經在跑，而且它的每一個分支都對冪等鍵的語意做了假設。本設計把那些假設當成**約束**（D6、D5、D7 各自正面處理其中一條），而不是事後才發現的相容性問題。

約束：PostgreSQL 16；金額一律 `BIGINT`／int64 最小貨幣單位（TWD 的最小貨幣單位是「元」）；公開 API 一律 `/api/v1`，**D13 的破例窗口已於 change `order-extras` 用盡並明文關閉**——本變更必須純 additive；`api/openapi/openapi.yaml` 與其四道契約檢查會因端點形狀改變而失敗，必須同步更新。

## Goals / Non-Goals

**Goals:**

- 讓「重送一次結帳請求」成為**安全**操作：同一把 key 的第 N 次送達 MUST 回到第一次的結果，MUST NOT 建立第二筆訂單、MUST NOT 第二次扣庫存。
- 這個保護必須住在**平台**，讓每一個自帶前端的商家自動獲得，而不是各自在前置層重寫一次。
- 並發帶同一 key 的兩個請求 MUST 有**確定的、經測試證明的**行為，MUST NOT 是競態。
- 商家 A MUST NOT 能以任何方式回放商家 B 的 key。
- 未帶標頭的請求 MUST 與本變更前逐位元組相同——這是預設，且 MUST NOT 有任何「本商家強制要求」的開關。
- 既有的條件式扣庫存與其受影響列數檢查 MUST NOT 被觸碰；三個既有 `-race` 測試 MUST 一行不改地通過。
- 純 additive：MUST NOT 動用 D13 破例窗口。

**Non-Goals:**

- 不為付款發起、訂單取消或購物車寫入端點加冪等鍵（D9）。
- 不做背景清理排程（D8）。
- 不做跨商家或跨端點共用的 key 命名空間（D4）。
- 不儲存任何回應主體或任何 bearer 憑證（D5）。
- 不對 key 施加結構要求（UUID 等），只施加長度與字元集界限（D2）。
- 不讓冪等鍵成為必填，也不提供 per-shop 強制設定。
- 不做「回放時回傳原本那一枚訂單存取權杖」——它從未被儲存，也不該被儲存（D5）。

## Decisions

### D1. 正面處理 `guest-checkout` design D11：它的三個理由，兩個仍然成立，第三個是誤判

D11 的原文結論是「不做冪等鍵；重複送出的後果明寫於 spec」，並把它記為將來的候選變更。本變更推翻它，因此必須逐條回應，而不是假裝那個決定不存在。

**理由一：「冪等鍵是一套需要獨立設計的機制……塞進本變更會讓它變成兩個變更。」**
**仍然完全成立，而且本變更就是它預言的那個形式。** D11 列出的四個未決問題（鍵的作用域與儲存、TTL、回放時回傳原回應還是 409、相同鍵不同 body 的處置）在本 design 分別由 D4／D8／D5／D7 回答——每一條都花了一整節，這正說明當初不把它塞進 guest-checkout 是對的。**這不是被推翻的理由，是被兌現的理由。**

**理由二：「它要解決的問題（重複下單）是可逆的（取消即可），與扣庫存的不可逆錯誤不在同一嚴重性等級。」**
**技術上仍然成立，本變更不主張它錯。** 重複訂單確實可以取消，庫存確實會歸還。但 D11 用這一點論證的是「所以可以晚一點做」，而不是「所以永遠不必做」——它自己就把冪等鍵列為候選變更。今天要做的理由不是嚴重性升級了，是**成本結構變了**：可逆性是**商家的**人工成本（有人要發現、判斷、取消、可能還要向顧客解釋），而且「可逆」不等於「可偵測」——顧客與商家都得先發現有兩筆單才談得上取消。以前這個成本是零（沒有外部消費端，沒有人會產生重複訂單）；ONDO 接入後它變成一個每天都可能發生的營運負擔。

**理由三：「前端以停用送出按鈕處理雙擊是標準作法，已寫入接入說明。」**
**這一條是誤判，也是本變更真正推翻的部分。** 它把問題描述成「使用者手滑點兩次」，那確實由停用按鈕解決。但真實的問題是另一個：**回應遺失時，客戶端無法區分「請求沒送到」與「請求送到了、訂單建了、只是回應在回程掉了」。** 停用按鈕對這件事完全無效——按鈕在收到回應後就會恢復，而顧客面對「訂單送出失敗，請檢查網路」的畫面，唯一的合理動作就是再按一次。

而這不是理論：**ONDO 的 UI 早就有「重新送出」按鈕**（`state.submit.status === 'error'` 時的文案），因為那是它唯一能回答顧客「我的單到底成立了沒有」的方式。它之所以敢這樣寫，正是因為它自己的 Worker 有冪等鍵。把它接到一個沒有冪等鍵的平台上，那顆按鈕會從「安全的重試」變成「保證建第二筆單」。

**「這個區分只有伺服器能提供」是本變更的全部立足點。** 客戶端無論怎麼寫都做不到：它可以在重試前先查一次訂單，但它沒有訂單 id（那正是遺失的那個回應要帶回來的東西），而以 email 查訂單需要會員 session——訪客沒有。冪等鍵是唯一能讓客戶端安全重試的機制。

**還有一個 D11 當時不存在的論點：消費端的數量。** D11 寫於「ONDO 即將接入」的時點，隱含的假設是單一消費端可以在自己那端處理。今天的架構決定是 ONDO 的 Worker 退場、平台成為唯一訂單權威，而 ONDO 是第一個自帶前端的商家、不是唯一一個。**一個必須由每個消費端各自正確實作、且錯了不會噴錯只會多一筆訂單的保護，本質上就是平台的責任。**

**D11 沒有錯的地方，也要記錄：** 它把這件事明確列為候選變更而非「想過所以不必做」，並把後果寫進了 spec 與接入說明。因為它這麼做，本變更的起點是一個**已知的、有記錄的缺口**，而不是一個事後才發現的 bug。

### D2. 標頭是 `Idempotency-Key`，值為不透明字串，只施加界限不施加結構

**名稱。** `Idempotency-Key`：Stripe 用它，IETF 的 `draft-ietf-httpapi-idempotency-key-header` 用它。發明第三個名字換不到任何東西，而用業界慣例換到的是「ONDO 的下一個工程師不必讀我們的文件也猜得到」。

**值的界限：8–255 個可見 ASCII 字元（0x21–0x7E）。** 不符即 `422 invalid_idempotency_key`。

| 界限 | 理由 |
| --- | --- |
| 下界 8 | **這一條是保護客戶端不被自己的 bug 靜默傷害。** 一把 `"1"` 這樣的 key 幾乎保證與同一商家其他顧客的 key 相撞，而相撞的後果是**對方結不了帳**（不同 body → 422 reused），不是一個看得出來的錯誤。8 對任何真實產生器都寬鬆得可笑（UUIDv4 是 36，ONDO 的 `k-…` 約 20），對事故則是一道免費的欄杆 |
| 上界 255 | btree 索引鍵的合理上限；任何超過它的值只可能來自 bug 或濫用。這是一個**未認證**端點，不設上界等於接受任意大小的索引鍵寫入 |
| 可見 ASCII | 排除控制字元與換行（日誌注入）、排除多位元組編碼歧義。key 出現在日誌與 psql 裡的機會很高，讓它永遠可讀是便宜的 |

**刻意不施加結構。** 不要求 UUID、不要求前綴、不做 base64 檢查。IETF 草案明文要求伺服器把值視為不透明；而具體地說，要求 UUID 會直接拒絕 ONDO 現有的產生器（`k-<base36 時間>-<base36 隨機>`），換到的是零——我們不解讀 key 的任何一個位元，只拿它當索引鍵。

**已評估並否決：由伺服器產生 key 並在某個「開始結帳」端點發放。** 那需要一條新端點、一次額外往返，而且**它解決不了問題**：如果取 key 的那次請求逾時，客戶端一樣不知道自己有沒有拿到 key。冪等鍵必須由**發起重試的那一方**產生，這是機制成立的前提。

**已評估並否決：把 key 放進請求 body。** ONDO 的 Worker 今天就是這樣（`body.key`），所以這是「改動最小」的選項。否決有三個理由，由弱到強：(1) 兩個端點的 body 形狀不同（會員是平鋪的收件資訊、訪客是巢狀），加在 body 裡就是加兩次；(2) body 裡的 key 會進入 D7 的請求雜湊，於是 key 自己是自己雜湊的輸入，語意糾纏；(3) **決定性的**——冪等是 HTTP 層的性質，不是這個 API 的業務欄位。放在標頭，一個泛用的重試中介層（或未來的 SDK）可以在不理解 body 的情況下加上它。

### D3. 儲存在 PostgreSQL，不在 Redis，而且預約的定案與訂單的建立在同一個交易內

**PostgreSQL 而非 Redis。** Redis 在本專案裡有一個明確且一致的定位：**快取與限流，故障時 fail-open**（`ratelimit` 的既有慣例）。把訂單去重放上去只有兩種結局，兩種都不能接受：

- **fail-open**：Redis 掛了 → 標頭被靜默忽略 → 重試建第二筆單。**這個機制會在最需要它的時候（系統不穩、逾時變多）恰好失效。**
- **fail-closed**：Redis 掛了 → 所有結帳失敗。這比本變更前的可用性**更差**——今天 Redis 掛了結帳照常運作。用一個防重複的功能換掉下單的可用性，方向是錯的。

而且還有第三個更根本的理由：**「這把 key 對應哪一筆訂單」與「那筆訂單」必須同生共死。** 訂單在 Postgres，把對應關係放在另一個儲存體意味著兩者可以獨立遺失。Redis 的 TTL 是免費的，但它換到的免費不值這個代價。

**表 `checkout_idempotency_keys`：**

```
id               serial PK
shop_id          int NOT NULL              ← 租戶資料，註冊進 tenant.tenantOwned
idempotency_key  varchar(255) NOT NULL
request_hash     char(64) NOT NULL         ← 原始 body 的 SHA-256 hex（D7）
status           smallint NOT NULL         ← 0 in_progress / 1 completed
order_id         int NULL                  ← 資訊性欄位，無 FK（見下）
expires_at       timestamptz NOT NULL      ← 每列自帶，不倚賴任何排程（D8）
created_at, updated_at

UNIQUE (shop_id, idempotency_key)          ← 仲裁者
CHECK  status IN (0, 1)
CHECK  (status = 0 AND order_id IS NULL) OR (status = 1 AND order_id IS NOT NULL)
```

第二條 CHECK 把「completed ⟺ 有訂單」變成資料庫事實，而不是一句只活在 Go 裡的約定——同一種紀律，同一個理由：下一個寫入這張表的人不必記得它。

**`order_id` 無 FK，是資訊性欄位。** 沿用 `orders.shipping_method_id` 與 `order_items.product_id`／`sku_id` 的既有慣例（`order-extras` design D4、`order-management` design D4）。這裡的具體理由是：optional 的 ent edge 會產生 `ON DELETE SET NULL`，而 SET NULL 會**直接違反上面那條 CHECK**——一個永遠不該發生但一旦發生就讓資料庫自相矛盾的組合。本 API 沒有任何刪除訂單的路徑（全樹零 `DELETE /orders`），所以無 FK 的成本是零，而它換掉的是一個結構性的地雷。

**UNIQUE 是 Postgres 預設的 NULLS DISTINCT。** 兩個欄位都是 NOT NULL，所以這個區別在這裡不產生任何行為差異——但必須明寫，因為本專案有兩處刻意使用 `NULLS NOT DISTINCT` 的手寫約束（`site_shop`、`role_user`），而 CLAUDE.md 已經記載過「勿誤套」。這張表由 ent 完整表達，**不需要手寫 migration**。

**預約的定案發生在 `Checkout` 的交易內，這是本節最重要的一句。**

天真的做法是三步：預約（INSERT）→ 呼叫 `Checkout`（自己的交易，commit）→ 標記完成（UPDATE）。它有一個小但真實的窗口：commit 成功之後、UPDATE 之前若行程崩潰或連線斷掉，**訂單存在而 key 仍是 in_progress**。此後在 TTL 內的每一次重試都拿到 409，TTL 過後的重試會建立**第二筆訂單**——恰好是這整個機制存在的目的所在，在一個罕見情況下失效。

因此：`order.CheckoutInput` 新增一個選填的預約識別碼，`Checkout` 在自己的交易內、**建立完 `orders` 與 `order_items` 之後、`Commit()` 之前**，多做一次條件式 UPDATE：

```go
if in.IdempotencyReservationID != nil {
    n, err := tx.CheckoutIdempotencyKey.Update().
        Where(idem.IDEQ(*in.IdempotencyReservationID), idem.StatusEQ(StatusInProgress)).
        SetStatus(StatusCompleted).SetOrderID(o.ID).Save(ctx)
    // err 或 n != 1 → rollback 整筆交易
}
```

於是「訂單存在」與「key 已完成」成為**同一個原子事實**。受影響列數檢查是本專案到處都在用的同一個慣用法。

**這對扣庫存保證的影響：零，而且是可論證的零。** 新增的 UPDATE 落在扣庫存迴圈**之外**、在迴圈**之後**，操作的是一個**本次請求剛剛以唯一索引獨佔取得**的資料列——沒有任何其他交易會競爭它，因此不引入新的鎖等待、不改變鎖取得順序、不可能造成死鎖。迴圈本身逐字未動。證據義務仍然由三個既有 `-race` 測試承擔，它們一行不改地保留。

**已評估並否決：把整段冪等邏輯做成 HTTP 中介層。** 中介層看不到交易，只能包住 handler 並在回應寫出後標記完成——那正是上面那個有窗口的三步做法，而且窗口更大（涵蓋整個回應序列化）。中介層在「快取任意端點的回應」這種泛用場景裡是對的形狀；在「這把 key 對應那一筆訂單」這種需要與領域交易同生共死的場景裡不是。

**已評估並否決：讓預約與訂單共用同一個交易（連 INSERT 也在裡面）。** 那樣唯一索引的衝突會在交易內爆炸並回滾整筆，於是「偵測到重複」與「回滾一個已經開始的結帳」綁在一起——並發的第二個請求會在扣完庫存之後才發現自己是重複的。先預約、後結帳讓重複請求**根本不會碰到庫存**。

### D4. key 的唯一性以 `(shop_id, key)` 為界——租戶隔離是要求，不是選配

**商家 A MUST NOT 能回放商家 B 的 key。** 三道各自獨立的防線：

1. **唯一索引本身是 `(shop_id, idempotency_key)`**：同一個字串在兩家商家是兩列，彼此不可見。
2. **所有查詢顯式帶 `shop_id`**：`WHERE shop_id = ? AND idempotency_key = ?`。shop_id 來自 TenantMW 解析的租戶上下文，永遠不來自請求 body。
3. **表註冊進 `tenant.tenantOwned`**：interceptor 在租戶上下文下自動加 `shop_id`，作為 defense in depth（與 members 的處置同型——顯式帶上，不倚賴 interceptor，但兩者都在）。

即使兩家商家的顧客碰巧產生了同一把 key，兩邊的結帳都正常運作、互不影響、互不可見。這一點以整合測試逐格覆蓋（同 key 在 shop A 完成後在 shop B 仍可正常建單，且 shop B 拿到的是自己的新訂單而不是 shop A 的回放）。

**唯一性刻意 NOT 包含端點。** 也就是說，同一把 key 先打訪客結帳、再打會員結帳，第二次會被當成重複。這看起來像是把兩件不相干的事綁在一起，但方向是對的：**key 表達的是客戶端的一次購買意圖**，而不是「對某條路由的一次呼叫」。若把端點放進唯一性範圍，同一把 key 就能合法地建立兩筆訂單——那正是這個機制存在的目的的反面。實務上第二次會因為指紋不同（兩條路徑的呼叫者範圍字串不同，D7）而收到 `422 idempotency_key_reused`，也就是「你重用了一把已經用掉的 key」，這是正確且可理解的答案。

**已評估並否決：把 key 的範圍縮到 `(shop_id, member_id/email, key)`。** 看似更安全，實際更糟：訪客結帳在解析出身分**之前**就必須決定要不要回放（回放時根本不該建立身分），把身分放進鍵會逼出一個「先建身分再判斷重複」的順序，而那正是重複請求應該避免觸碰的東西。

### D5. 回放回傳 201 ＋ 同構的 body；訪客路徑**重新簽發**訂單存取權杖

**狀態碼：201，與第一次完全相同。**

Stripe 的做法是回放原本的狀態碼，本設計採同一立場，理由具體且可驗證：**ONDO 的 `handleSubmitResponse` 寫的是 `if (status === 201)`。** 若回放回 200，那個分支不會進，於是一筆真實存在的訂單會在顧客眼前顯示為錯誤——而且是在他已經按過一次「重新送出」之後。要避免這件事，每一個消費端都必須學會第二個成功碼；用一個純粹分類學上的正確（「這次沒有 create 所以不該是 201」）換掉每個消費端的一次踩坑，不划算。

更根本地說：冪等的定義就是**重試的表現要像原本那次請求**。一個能被狀態碼分辨出來的回放不是冪等，是「另一種成功」。

**body：與第一次同構。** 訪客路徑回 `{order, order_access_token, token_type, expires_in}`，會員路徑回 `orderJSON(order)`。`order` 是**當下**從資料庫讀出來的那一筆，所以若期間訂單已被付款或取消，回放看到的是**現在的**狀態，不是一份凍結的舊回應。這是刻意的：我們儲存的是「這把 key 對應哪一筆訂單」，不是一份回應快照。回應快照會隨時間變成謊言，而客戶端拿到回放之後最想知道的恰恰是這筆單現在怎麼樣了。

**診斷用的回應標頭 `Idempotency-Replayed: true`。** 正因為 body 與狀態碼刻意不可分辨，接入時「我的 key 到底有沒有生效」就完全無從驗證。一個回應標頭把可觀測性還給接入者，同時不進入 body（因此不受 `additionalProperties: false` 影響、不佔用 v1 表面鎖的一行、不成為資料契約的一部分）。第一次請求不帶這個標頭。

**訂單存取權杖：重新簽發，不回傳原本那一枚。**

原本那一枚**沒有被儲存，而且不該被儲存**——它是 bearer 憑證，`guest-checkout` design D3 選擇無狀態 JWT 的整個理由就是不必存它。即使存了也不能用：它帶著原始簽發時刻的 `exp`，一次 20 小時後的回放會回傳一枚只剩 4 小時的權杖，而 25 小時後的回放會回傳一枚**已經過期**的權杖——一個形狀像成功、實際無用的回應，是最糟的一種。

重新簽發不擴大任何授權：新權杖的 `sub` 是同一筆訂單、`aud` 是同一個 `order:{shop_id}`，能做的事與原本那枚逐字相同（讀該單、對該單發起付款、讀該單出貨）。`expires_in` 因此永遠誠實地描述**這個回應裡這一枚**權杖。

**代價，誠實記錄：** 持有 key ＋ 原始請求原始位元組的人，可以在 TTL 內反覆取得該訂單的新權杖，等於把訂單存取能力延長到「冪等 TTL ＋ 權杖 TTL」（預設 24h + 24h）。但能通過 D7 雜湊比對的人，本來就完整持有那次請求的全部內容（email、收件姓名、電話、地址、品項）——他從回放取得的不是新資訊，只是一個他早就能從自己手上那份請求重放出來的能力。記入 Risks。

### D6. 沒有建立訂單的請求**不佔用** key——這不只是體面，是相容性的硬需求

**決定：任何未成功建立訂單的請求都釋放預約，該 key 立即可重用。** 涵蓋：JSON 解析失敗（400）、輸入驗證失敗（422）、庫存不足（422）、顧客已被停用（422）、限流（429，此時根本還沒預約）。

Stripe 的做法是連錯誤回應也一併回放。本設計不採用，理由由弱到強：

1. **回放錯誤買不到東西。** 錯誤是請求主體的確定性函數，而主體已經被雜湊比對過了（D7）——同一把 key ＋ 同樣的位元組，重跑一次必然得到同樣的錯誤。儲存它省下的是一次驗證，付出的是一整張表的狀態機複雜度。
2. **它會把「暫時性失敗」凍結成永久失敗。** 庫存不足是最典型的：顧客等商家補貨後重送同一把 key，卻永遠拿到同一個「庫存不足」——而真正的庫存已經有了。
3. **（決定性）ONDO 現有的程式碼依賴這個行為。** `handleSubmitResponse` 的 400 分支寫的是 `state.submit = { status:'idle', key: key, ... }`——**它刻意保留同一把 key**，讓顧客修正欄位後再送一次。若失敗佔用 key，這條路徑會壞得很難看：顧客改好了電話，重送，然後得到 `422 idempotency_key_reused`（因為 body 變了）或一份被凍結的舊錯誤——兩者都讓他**永遠送不出去**，除非他知道要離開結帳頁再進來一次（那才會產生新 key）。

第 3 點同時說明了為什麼「失敗只保留雜湊、不保留回應」也不行：修正欄位必然改變 body，改變 body 必然改變雜湊，於是必然撞上 reused。**完整釋放是唯一能讓「修正後重送」這條標準流程走得通的選擇。**

**這削弱了什麼？誠實回答：一點點。** 一個會反覆送出必然失敗的請求的客戶端，不會被冪等鍵擋下來——但它本來也就沒有建立任何訂單，該擋它的是限流（訪客結帳既有的兩條規則），不是冪等鍵。冪等鍵的職責是「不要建立第二筆訂單」，對一個建立了零筆訂單的請求，它沒有職責。

**實作上的細節，明寫以免日後被「順手改成 defer」翻案：** 釋放是一次帶 `WHERE status = in_progress` 的 DELETE。加上這個條件是為了讓它不可能刪掉一列已經完成的預約——即使呼叫順序日後被人改錯。

### D7. 相同 key 不同請求：以「呼叫者範圍 ＋ 原始位元組」的 SHA-256 指紋比對，不符即 `422 idempotency_key_reused`

**為何要比對。** 沒有這道檢查，冪等鍵就變成「同一把 key 的第二次請求無論送什麼都回放第一筆訂單」——顧客改了地址、加了一項商品，然後拿到一筆與他剛送出的內容不同的訂單，且完全不知道發生了什麼。**靜默地用舊資料回應新意圖**是比多建一筆訂單更糟的失敗模式。

**雜湊什麼：`呼叫者範圍 || "\n" || 原始請求主體位元組`，SHA-256，存 hex。** 主體不做任何正規化。

**「呼叫者範圍」不是裝飾，它堵住一個真實的跨顧客洩漏。** D4 讓 key 的唯一性以 `(shop_id, key)` 為界（刻意不含身分，理由見該節）。若指紋只涵蓋主體，會出現這個情形：

> 同一家商家的會員 A 與會員 B 各自產生了同一把弱 key，而會員結帳的主體只是收件資訊——**兩個人寄到同一個地址（送禮、公司地址、同住家人）就會產生逐位元組相同的主體**。於是 B 的結帳會回放 A 的訂單，B 看到的是別人的訂單內容。

這不是理論邊角：會員結帳的主體恰好是本 API 中最容易在兩位顧客之間重複的一份資料。因此指紋定義為：

```
member-checkout:<memberID>  \n  <raw body>      會員結帳
guest-checkout              \n  <raw body>      訪客結帳
```

- **會員路徑**：範圍含 `memberID`，兩位會員的指紋必然不同 → B 得到 `422 idempotency_key_reused`，看不到 A 的任何資料。
- **訪客路徑**：範圍是常數，但主體本身含 email——兩位訪客要撞上必須連 email、品項、收件資訊全部逐位元組相同，那時他們表達的**就是同一個購買意圖**，回放是正確答案。
- **跨端點**：兩條路徑的範圍字串不同，因此 D4 所說的「同一把 key 先打訪客、再打會員」必然落在 422，而不可能落在一次錯的回放。

作為 defense in depth，會員路徑的回放另以**會員範圍的**訂單查詢取回訂單（既有的 `GetOrder(shopID, memberID, orderID)`，非本人即 `ErrNotFound`）——即使指紋日後被改壞，也不會變成水平越權。

**為何範圍不併進唯一索引而是併進指紋。** 併進索引等於允許同一把 key 在不同身分下各建一筆訂單（D4 已論證那是機制目的的反面）；併進指紋則是「同一把 key 只能屬於一個購買意圖，第二個意圖一律拒絕」。前者放行，後者拒絕——在一個防重複的機制裡，拒絕才是安全的預設。

**已評估並否決：正規化主體後再雜湊**（解析成結構、重新序列化、忽略空白與鍵順序）。它聽起來更寬容，但有一個致命性質：**它只忽略我們今天知道要忽略的差異。** 正規化必然是「解析成已知欄位再輸出」，於是任何我們還沒加進結構的欄位都會被抹掉——當下一個變更新增一個選填鍵時，兩個在該鍵上不同的請求會雜湊成同一個值，而回放會回傳錯的那一筆。原始位元組沒有這個問題，而且它的定義永遠不需要維護。

**代價，明寫給消費端：重試 MUST 送出與原本逐位元組相同的主體。** 對任何以同一個物件走同一條序列化路徑重送的客戶端（也就是每一個實務上的重試），這是自動成立的——ONDO 的 `submitOrder()` 就是從同一份 `state` 重建同一個物件再 `JSON.stringify`。會踩到的是「重試時順手改了點東西」的客戶端，而那本來就應該是一把新 key。這一條在 `docs/storefront-integration.md` 用一句話講清楚。

**狀態碼與 code：`422 idempotency_key_reused`，`details` 為空。** 422 的既有語意是「解析成功但違反規則」，正是這裡的情形。不放 `details` 是因為既有的 `details[].pointer` 慣例是**相對於請求主體**的 JSON Pointer，而這個問題出在標頭上——硬造一個指向 `/` 的 pointer 只會讓那個慣例變得不可信。改用一個專屬 code 承載全部資訊，與既有的 `checkout_unavailable`、`registration_failed` 同型。

### D8. TTL 24 小時，以每列自帶的 `expires_at` 判定；逾期列由後續同鍵請求原子接管

**為何 24 小時。**

下界由重試的真實跨度決定：ONDO 是 15 秒逾時 ＋ 人為重按，那是**秒到分鐘**的量級；但顧客關掉分頁、傍晚想起來再打開同一個結帳頁重按一次也完全正常，那是**小時**的量級。

上界由一個反向的失敗模式決定，這一點值得寫清楚：**TTL 太長會讓「顧客隔天真的想再買一次同樣的東西」被靜默地當成重試。** 這在客戶端正確的情況下不會發生（key 應該每次結帳重新產生，ONDO 的 `resetCheckout()` 正是如此），但客戶端一旦寫錯——例如把 key 存進 `localStorage` 忘了清——症狀會是「顧客按了送出，看到一筆舊訂單，錢沒收到，商家也沒收到單」。**這種失敗是靜默的、雙方都看不出來的**，比多建一筆訂單難查得多。TTL 是這個錯誤的自然上界。

24 小時同時與平台既有的另一個決定對齊：`ORDER_ACCESS_TOKEN_TTL` 也是 24 小時，理由同樣是「涵蓋當天、隔天失效」（`guest-checkout` design D3）。一個系統裡少一種要記的時間長度是有價值的。可由 `CHECKOUT_IDEMPOTENCY_TTL` 調整。

**逾期以列上的 `expires_at` 判定，而不是以 `created_at + 設定值` 現算。** 兩個理由：(1) 調整設定不會回溯改變既有列的意義——一列在寫入時就承諾了自己活到什麼時候；(2) 判斷變成一次普通的欄位比較，不需要任何一致的時鐘算術散落在多個查詢點。

**逾期列的處置：由下一個用同一把 key 的請求原子接管，不做背景排程。**

```sql
UPDATE checkout_idempotency_keys
   SET request_hash = ?, status = 0, order_id = NULL, expires_at = now() + ttl, updated_at = now()
 WHERE shop_id = ? AND idempotency_key = ? AND expires_at <= now()
```

受影響列數 = 1 表示本次請求接管了這把過期的 key（等同一次全新的預約）；= 0 表示它還沒過期，走正常的判斷路徑（回放／409／422）。**又是同一個受影響列數慣用法**，因此接管本身是並發安全的：兩個同時到達的請求只有一個會拿到 1。

**不做背景清理排程，這是一個有成本的取捨，明寫。** 沒被接管的逾期列會留在表裡。成長的界限是「曾經用過的相異 key 數」，而它的速率由訪客結帳既有的限流規則封頂（每個 shop+IP 每 10 分鐘 20 次）。以花店的量級這在可見的未來都不是問題。**觸發重新評估的條件是明確的：這張表的列數變成一個要拿出來討論的數字。** 屆時加一支 `DELETE WHERE expires_at < now() - grace` 是純 additive 的，不需要改動本變更的任何資料模型或語意——這正是把逾期判定放在 `expires_at` 而不是放在「列還在不在」的好處：**清理是純粹的空間回收，永遠不影響正確性。** 同理，現在不為 `expires_at` 加索引（沿用 `order-extras` design D3 對 `requested_delivery_date` 的同一判斷：欄位型別決定它日後加得成，現在加是為想像中的查詢付現金）。

### D9. 只有兩個結帳端點納入；付款發起明確評估後不納入

本變更的驅動力是一個具體的、已知的消費端需求，因此範圍以「哪裡真的會建立重複的不可逆資源」為準，而不是以完備為準。

| 端點 | 納入？ | 理由 |
| --- | --- | --- |
| `POST /shop/guest/checkout` | **是** | 驅動需求本身。自帶品項、天然可重入、重送即第二筆訂單 |
| `POST /shop/checkout` | **是** | 見 D10 |
| `POST /shop/orders/{id}/payments`<br>`POST /shop/guest/order/payments` | 否 | 見下 |
| `POST /shop/orders/{id}/cancel` | 否 | 第二次呼叫由既有的條件式 flip 回 409，且不產生第二個資源。它已經是收斂的 |
| `/shop/cart/*` | 否 | 不建立訂單、不扣庫存；重複加入的後果是購物車數量，顧客看得到也改得掉 |

**付款發起，正面論證為何不做。** 它是本變更最接近邊界的候選，所以要說清楚：

1. **重送不會產生第二筆訂單，也不會多收一次錢。** `InitiatePayment` 既有的狀態守衛（已取消 → 409、`payment_status != unpaid` → 409）已經擋住第二次成功的發起。重送真正產生的是一列 `status = pending` 的付款嘗試，而它永遠等不到 webhook（金流商那邊的參照不同），因此不會推進任何訂單狀態。
2. **真正的請款冪等權威在金流商那一側**，以 `(provider, provider_reference)` 表達，本專案的 webhook CAS 已經正確消費它。在我們這一側再加一層，防的是「多一列 pending」，而不是「多收一次錢」。
3. **目前唯一的 provider 是 mock**，它的 `InitiatePayment` 沒有任何外部成本。真實 provider 接入時，若其發起動作本身有成本或有速率配額，那才是重新評估的時機——**明確記錄為觸發條件**，而不是「想過所以永遠不必」。
4. 沒有消費端要求它。ONDO 的付款是一次導向，不是一個會重試的寫入。

### D10. 會員結帳一併納入——因為它的既有保護解決的不是同一個問題

這是本變更唯一一項「範圍是否該擴張」的判斷，因此必須論證而不是宣稱。

**看似不必做的理由：** 會員結帳已經有防護——購物車的 `Active → Converted` CAS，第二次呼叫回 409。而且沒有消費端要求。

**為何仍然要做：那個 CAS 解決的是另一個問題。**

購物車 CAS 回答的是「這台車已經結過帳了」。它**不回答**「我剛才那次請求成不成立、訂單是哪一筆」。在回應遺失的情境下，客戶端拿到 409 之後仍然一無所知——它甚至不能確定那個 409 是**自己**造成的（也可能是顧客在另一個分頁結的）。於是它只有兩條路：對顧客顯示錯誤（一筆成功的購買顯示成失敗），或去 `GET /shop/orders` 猜哪一筆是剛才那筆（一個沒有正確答案的啟發式——同樣品項的兩筆單看起來一模一樣）。

而顧客面對「結帳失敗」的畫面時，最自然的動作是**重新把商品加進購物車再結一次**——舊車已經 Converted，新車是全新的，CAS 不會擋住任何東西。**於是會員路徑也會產生兩筆真實訂單**，只是多繞了一段路。這條路徑需要顧客配合，因此比訪客路徑罕見，但它是同一個病因（回應遺失無法判定）的同一個症狀。

**其餘理由：**

- **成本是負的。** 機制寫在 `order.Service.Checkout`（預約定案）與一個 handler 共用輔助裡。兩個 handler 都經過那個輔助；**排除會員路徑要多寫一個 `if`，不是少寫一個。**
- **一條規則比兩條便宜。** `docs/storefront-integration.md` 同時描述兩條路徑。「兩個結帳端點都接受 `Idempotency-Key`」是一句話；「訪客可以但會員不行」需要一段解釋，而且那段解釋沒有好答案。
- **它與 `order-management` 既有的不變式同向。** 「所有下單路徑共用單一結帳實作」（該 spec 的既有 requirement）的精神是：下單相關的保護只能有一份實作。讓冪等保護只在一半的入口生效，是對那條不變式的違反的溫和版本。

**代價，誠實記錄：** 測試面積變大（兩條路徑各需並發、回放、跨商家覆蓋），契約要同步兩個端點。接受。

**已評估並否決：只做訪客、把會員留給「有人要求時」。** 那個時刻的成本會比現在高——屆時要重新讀一次本 design、重新做一次契約更新、重新寫一輪測試，而且中間這段時間文件要維護一條不對稱的規則。這不是 YAGNI 適用的形狀：這裡沒有「猜測未來需求」，機制已經在了，問題只是要不要在第二個呼叫點也接上去。

### D11. 並發同 key：輸家拿 `409 idempotency_key_in_progress`，且**保證不建立第二筆訂單**

兩個帶同一把 key 的請求同時到達，唯一索引決定勝負：

```
請求 A: INSERT (shop, key, hash, status=in_progress)  → 成功，A 擁有這把 key
請求 B: INSERT 同上                                    → UNIQUE 違反
        → 載入既有列判斷：
             雜湊不符            → 422 idempotency_key_reused
             status=in_progress → 409 idempotency_key_in_progress   ← 本節
             status=completed   → 回放（D5）
```

**輸家絕不進入 `Checkout`。** 這是本節最重要的性質，也是「並發帶同一 key 只建立一筆訂單、庫存只扣一次」這個保證的來源：B 在**碰到任何領域邏輯之前**就退出了。以 `-race` 的並發測試證明（N 個帶同一 key 的請求同時發出 → 恰好 1 筆訂單、庫存恰好扣 1 次、恰好 1 個 201，其餘全部是 409 或回放的 201）。

**為何回 409 而不是等待勝者完成再回放。** 等待需要輪詢或 advisory lock 加逾時，會在一次結帳交易的全長內佔住一條 HTTP 連線與一條資料庫連線，而且把一個立即的答案變成一個慢的答案。而回 409 對客戶端來說是**安全**的：稍後重試不是拿到回放（勝者成功了），就是拿到一次全新的預約（勝者失敗並釋放了 key，D6）。**客戶端的重試迴圈在兩種設計下是同一段程式碼**，所以等待買到的只有「少一次往返」，卻付出連線佔用與逾時語意。

**為何是 409 而不是 429。** 429 的語意是「你太快了，配額用完了」，會誘導客戶端做退避與長時間等待；這裡的真實情況是「有一個同樣的請求正在跑，很快就會有答案」。用既有的 409 家族（衝突）配一個專屬 code，語意正確且不與限流混淆。刻意**不**附 `Retry-After`——那個標頭在本 API 是限流專屬的，借用它會讓「429 才有 Retry-After」這條既有的簡單規則變得有例外；建議的重試節奏寫在文件裡。

**殘留窗口，明寫：** 若勝者的行程在預約之後、交易定案之前崩潰，那列會停在 `in_progress` 直到 `expires_at`，期間的重試一律拿到 409。這是本設計裡唯一一個「訂單不存在但 key 被佔住」的狀態，它的代價是顧客在 TTL 內無法用同一把 key 重下這一單（離開結帳頁再進來會產生新 key，因此不是死路）。用 D3 的交易內定案換掉了更糟的那一半（訂單存在但 key 沒定案），剩下這一半只能靠 TTL 收斂——記錄為已知限制。

### D12. 本變更為純 additive，不動用 D13 的破例窗口

破壞性面向：**零**。逐項檢查：

- **無新增路由**，因此路由覆蓋檢查（契約檢查 1）的清單不變。
- **無移除任何路徑、回應鍵或 schema 屬性**，因此 v1 表面鎖（檢查 4）只會**新增**行。
- 新增的是一個**選填的請求標頭**：不帶時，兩個端點的行為與本變更前逐位元組相同。既有整合測試 MUST NOT 需要為了配合本變更修改任何斷言——這是驗收條件之一，也是「additive」最誠實的操作型定義。
- 新增的三個錯誤碼只在帶了標頭時才可能出現；沒有任何既有錯誤的狀態碼或 code 改變。
- 新增的 `Idempotency-Replayed` 是回應**標頭**，不進入 body，因此不受 `additionalProperties: false` 影響，也不改變任何回應 schema。
- 新增一張表，不改任何既有表的欄位、索引或約束。

D13 的破例窗口已於 change `order-extras` 用盡並明文關閉。**本變更不需要它**，這一節的存在是為了讓那件事被檢查過而不是被假設。

## Risks / Trade-offs

- **[未在 `wire.go` 接上冪等服務 → 標頭被靜默忽略，每一支整合測試仍全綠]** → 這是 change `commerce-demo-seed` 實測記錄過的失敗模式的完全同型（`wire.go` 零 Go 測試覆蓋，整合測試各自建 router）。緩解有二，兩者都做：(1) `e2e/commerce-path.mjs` 新增回放斷言——那是唯一會打到真實佈線的地方；(2) handler 在收到標頭卻沒有冪等服務時以 `Log.Error` 大聲記錄，而不是靜默通過。**不宣稱這是完全的防護**：e2e 不在 CI 內（同一個 change 的實測發現），所以它的可信度上限仍是「有人記得在本機跑」。

- **[持有 key ＋ 原始請求位元組者可在 TTL 內反覆取得該訂單的新存取權杖]** → D5 的必然結果。半徑：能通過雜湊比對的人完整持有那次請求的全部內容（email、收件人、電話、地址、品項），回放給不了他任何新資訊，只給一個他本來就能重放出來的能力。界限：冪等 TTL（24h）內；權杖本身的能力不變（單一訂單的讀取與付款發起，不含取消、不含訂單歷史、不可刷新）。

- **[勝者在預約後、交易定案前崩潰，key 卡在 in_progress 直到過期]** → D11 的殘留窗口。期間同 key 重試一律 409；顧客的出路是離開結帳頁再進來（產生新 key），不是死路。D3 已把更糟的另一半（訂單存在而 key 未定案）消除。**不宣稱窗口為零。**

- **[逾期列無背景清理，表會單調成長]** → D8 的明確取捨。速率由訪客結帳既有限流封頂；重新評估的觸發條件是「列數變成一個要討論的數字」；加清理是純 additive 且**不影響正確性**（逾期判定在 `expires_at`，不在「列還在不在」）。

- **[以原始位元組雜湊 → 重試時序列化有差異即 422]** → D7 的刻意取捨。實務上任何從同一份狀態重建同一個物件再序列化的客戶端都逐位元組相同；會踩到的是「重試時順手改了內容」的客戶端，而那本來就該是新 key。緩解：`docs/storefront-integration.md` 以一句話明講「重試要送一模一樣的位元組」，並說明 422 `idempotency_key_reused` 的意思就是「你改了東西卻沿用舊 key」。

- **[key 太短造成同商家不同顧客誤撞，症狀是對方結不了帳]** → D2 的下界 8 是針對這個。**不宣稱它能防住決心用固定 key 的客戶端**——那種客戶端的自己人（同一顧客）會先撞到，症狀立即可見。

- **[TTL 太長時，客戶端若錯誤地重用 key，真實的第二次購買會被靜默當成重試]** → D8 已把這個反向失敗模式列為 TTL 上界的決定因素。24h 是「涵蓋當天」與「隔天必定是新的一單」的交界。**這個失敗模式無法在伺服器端偵測**（我們無從分辨「重試」與「重用」），只能以 TTL 收斂並在接入文件明講 key 必須每次結帳重新產生。

- **[會員結帳納入 → 測試面積與契約維護面積變大]** → D10 的已知代價，接受。換到的是一條規則而非兩條，以及「下單保護只有一份實作」這條既有不變式不被破例。

- **[trade-off：每次帶 key 的結帳多一次 INSERT 與一次 UPDATE]** → 兩者都是主鍵／唯一索引上的單列操作；UPDATE 落在既有交易內、扣庫存迴圈之後，操作的是本次請求剛獨佔取得的列，不引入新的鎖競爭。不帶 key 的請求**一次額外查詢都沒有**。

- **[新增第一張以「客戶端提供的字串」為索引鍵的表，在一個未認證端點上]** → 長度與字元集界限（D2）＋ 訪客結帳既有的兩條限流規則 ＋ 1 MiB body 上限。key 不被系統解讀為任何格式，只當索引鍵與比對值。

## Migration Plan

1. ent schema：於 `api/internal/ent/schema/order.go` 新增 `CheckoutIdempotencyKey`（欄位、`UNIQUE(shop_id, idempotency_key)`、兩條 CHECK）；`go generate ./internal/ent`。
2. `internal/tenant` 的 `tenantOwned` 新增 `"CheckoutIdempotencyKey": true`。
3. `make migrate-gen name=add_checkout_idempotency` 產生 up/down。**檢查產生的 SQL 沒有順手提議 drop 掉手寫的 `UNIQUE NULLS NOT DISTINCT` 約束**（姊妹 change 踩過這個坑），並確認本表的 UNIQUE 是 Postgres 預設的 NULLS DISTINCT。
4. 重算 `atlas.sum`（以 `ariga.io/atlas/sql/migrate` 的 `WriteSumFile` 對 `migrations/` 重新雜湊；atlas CLI 未安裝於本環境）。
5. `make migrate` 套用。驗收：新表存在、既有表零變動、既有資料零變動。
6. 新增設定 `CHECKOUT_IDEMPOTENCY_TTL`（預設 24h），有預設值，`.env` 不設也能運作。
7. **部署順序無耦合**：平台先上線（未帶標頭的行為完全不變），ONDO 再改前端把 `body.key` 移到 `Idempotency-Key` 標頭。兩者之間沒有任何時序要求。

**Rollback**：`make migrate-down` 移除該表；程式面移除標頭處理即回到本變更前的行為。**沒有任何不可逆的部分**——訂單、庫存、點數、購物車一律不受影響，唯一遺失的是「哪一把 key 對應哪一筆訂單」的對應關係，而那份資料在回滾後本來就沒有讀取者。

## Open Questions

- **真實金流 provider 接入時，付款發起要不要也納入冪等鍵？** D9 已論證目前不做並記錄了觸發條件（provider 的發起動作本身有成本或配額）。屆時本變更的機制可以原樣複用——`idempotency.Service` 不知道自己保護的是結帳，唯一需要決定的是「回放時要不要重新向 provider 取得 `redirect_url`」，而那個答案取決於該 provider 的 session 語意。此刻決定等於猜測一個尚不存在的 provider 的行為。

- **後台要不要能看到一筆訂單是不是回放產生的？** 本變更不做：後台目前沒有任何要呈現這件事的畫面，而且從商家的角度「回放」不是訂單的性質（訂單就是訂單，回放只是它被取回了第二次）。若日後要做營運除錯，`checkout_idempotency_keys` 已經有 `order_id`，加一個唯讀查詢是 additive 的。

- **v1 表面鎖不涵蓋請求參數——要不要補？（實作中發現，記錄而不在本變更處理）** `v1-surface.txt` 收錄兩種行：路由（`METHOD /path`）與具名 schema 的屬性（`Schema.property`）。它**不收錄 `components/parameters`**，因此本變更**沒有在鎖檔裡新增任何一行**——`Idempotency-Key` 這個新的公開承諾目前不受鎖檔保護，日後有人把它從契約中拿掉，四道檢查全部沉默。這是鎖檔的真實粒度，不是本變更的疏漏；補它要改動 `openapi-contract` 能力的檢查邏輯與鎖檔格式（既有的四個參數也會一併入鎖），屬於那個能力的變更而不是這一個。**不順手做**的理由與本變更整體一致：驅動力是一個具體的消費端需求，不是機制的完備性。記為 `api-contract` 的候選後續。

- **`Idempotency-Key` 要不要擴散到後台的寫入端點？** 後台的消費端是第一方 admin SPA，它的失敗模式與重試行為完全不同（有 session、有訂單列表可以核對、操作者是人）。目前沒有證據顯示那裡有同一個問題。真正會改變這個判斷的是「出現第一個第一方以外的後台消費端」——與 `openapi-contract` design 對 RBAC 機械化驗證所記錄的觸發條件相同。
